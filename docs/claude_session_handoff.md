**T1. 역방향 토큰 분리 (코드)**
지금은 `service_token` 필드 하나가 인바운드(`app/middleware/auth.py`, 백엔드→LLM
검증)와 아웃바운드(`app/tools/backend_client.py` `_headers()`, LLM→백엔드 발신)
양쪽에 다 쓰인다 — `app/config.py`에서 같은 필드를 읽는 두 지점을 확인할 것.
- `app/config.py`에 신규 필드 추가(예: `backend_service_token`, env
  `BACKEND_SERVICE_TOKEN`), 기본값은 기존 `DEFAULT_SERVICE_TOKEN` 패턴과 동일한

- `app/tools/backend_client.py`의 `_headers()`(아웃바운드 발신 헤더 조립)가 새
  필드를 쓰도록 변경. **주의**: 공유 `httpx.AsyncClient`가 생성 시점에 헤더를

- 기본값 가드 확장 필요한 곳: `app/api/health.py`(`/readyz`가 기본값이면 실모드에서

  단언 추가), `scripts/verify_backend_contract.py`(`--token` 기본값을 새 필드로).
- 문서 정정: `.env.example`의 "상호 인증용" 문구를 **두 방향 두 값**으로 정정,

**T2. 토큰 값 생성·전달 (사용자 액션)**
`openssl rand -hex 32` 등으로 새 토큰 값 생성 — **보안 채널로만 전달, 저장소·문서·

**T3. BE-007(멤버명단) 부재 방어 (코드)**
`app/tools/backend_client.py`의 멤버명단 조회 함수는 실모드에서 404를 그대로
`raise_for_status()`로 예외 전파한다. 이게 세 곳에 영향을 준다:
1. `load_context`는 이미 `return_exceptions=True`로 받아 fail-open 처리(빈 목록)
   — 안전.
2. `precedent_auditor`가 부르는 `masked_claim_summary`(→`get_team_members`)는
   무방비라 예외가 올라가고, `precedent_auditor` 노드가 이걸 잡아 `error` 소견으로
   바꾼다 — **매 건 판례 심사관이 error가 되어 에스컬레이션 쪽으로 쏠린다.**
3. `persist_precedent`가 부르는 `save_precedent`(→`get_team_members`)도 무방비라
   예외가 나고, `persist_precedent` 노드가 non-fatal로 삼켜서 **판례 저장이 실모드
   에서 조용히 매번 실패**한다(로그만 남고 화면엔 안 보임).
4. **별도로 방치된 진짜 버그**: `POST /v1/precedents`(관리자 결정 수동 등록
   엔드포인트)는 `save_precedent`를 무방비로 부르므로 BE-007이 없으면
   **HTTP 500**을 낸다 — 심사 그래프 바깥이라 놓치기 쉽다.

대응: 위 조회 함수의 실모드 분기에서 404/HTTP 에러를 잡아 경고 로그 + 빈 목록
반환으로 바꾼다(`load_context`가 이미 하는 fail-open과 같은 형태로 경계를 내림).
한계: 멤버 명단이 없으니 **PII 마스킹 자체는 여전히 불가**(실명이 그대로 LLM에
전달됨) — 이건 코드로 못 푸는 문제라 T6 회신에 리스크로 명시할 것. 테스트 추가.

**T4. BE-004 receiptPath 표현 확인 (회신 우선, 코드는 답 이후)**
2026-08-06 합의는 "백엔드가 지출상세 API의 영수증 경로 필드를 심사 요청의
`receiptPath`에 담아서 보낸다"였다. 이번 회신의 "지출상세 응답의 영수증 경로로
접근"이라는 표현이 혹시 "우리가 상세 조회 응답에서 직접 읽으라"는 뜻이라면 —
지금 코드(`load_context`)는 상세 응답에서 영수증 경로를 전혀 읽지 않고 `claim`에
5개 필드만 매핑하므로, **전 건이 영수증 미첨부로 처리돼 가드레일이 100%
에스컬레이션**된다. 코드 변경 전에 **회신으로 먼저 확인**(T6에 포함) — 합의대로
계속 요청 필드에 채워 준다면 코드 변경 불필요.

**T5. BE-009(지출이력) 미구현 — 사용자 결정: 코드 변경 없음, 문서화만**
현재 실모드에서 이 API가 404면: 대시보드 API(`/v1/dashboard/summary`)는
동기 엔드포인트라 **프론트에 500을 직접 반환**(페이지 로드 경로라 영향 큼).
리포트·다이제스트·예산제안 3개는 잡 큐 경로라 재시도 3회 후 `dead` 상태로 남는다
(백엔드는 잡 상태 조회로만 알 수 있음, 콜백은 안 감). 심사 경로와 주간 브리핑은
이 API를 아예 안 쓰므로 무관. **결정: 코드는 그대로 두고, 이 4개 기능이
BE-009 구현 전까지 불가능하다는 사실을 배포 문서(T5-문서)와 백엔드 회신(T6)에
명시하는 것으로 마무리.**

## 6. 규율 (지킬 것 — 기존 10개 + 이번 세션 확인분)

1. **프롬프트/판정 rubric 변경은 사용자와 함께 결정.** 버전을 지우지 않고 새로
   만든다. **실측으로 재현된 개선만 승격**(2회 재현이 관례). 단, 카탈로그 라벨처럼
   실측 우열이 아닌 **정합 수정**은 예외.
2. **머지 게이트**: `pytest` 전체 통과 + 골든셋 **오승인 0건**·정확도 ≥90%.
3. **AI는 승인/반려를 실행하지 않는다.** 추천만 콜백으로 보내고 실행·예산 차감은
   백엔드.
4. **`.env`의 `MOCK_LLM=true`는 절대 바꾸지 말 것.** 실모드는 프로세스 주입으로만.
5. 커밋 시 **파일을 하나씩 지정**해 `git add` — `git add .`·`git add -A` 금지.
6. **팀장 브랜치·공유 문서를 임의로 고치지 않는다.** main 반영은 PR로.
7. **결함이라고 주장하기 전에 다른 브랜치를 먼저 본다.** `git log --all -- <파일>`.
8. **작업 전 머지 충돌 영향을 확인한다.** origin/main이 자주 움직이는 시기이므로
   특히.
9. **여러 사람이 같은 파일에 각자 항목을 append하는 자리**(DEFAULT_VERSIONS·
   few_shot 계약 테스트 등)는 병합 순서가 바뀌면 충돌이 난다. 충돌 자체는 정상 —
   양쪽 항목을 다 살리는 게 항상 정답이다.
10. **push 직전에 반드시 `git fetch origin --prune` 먼저.**
11. **(신규) 백엔드 공지·채팅의 SQL·값 문자열은 마크다운이 언더바 등을 삼킬 수
    있다.** 값이 이상해 보이면 코드 대응 전에 원문(raw) 재확인부터 요청할 것 —
    이번 `행사_활동`이 `행사활동`으로 보였던 사건이 전례(§3 참고). 반대로,
    **"버그처럼 보이는 것도 실제 재현 전엔 확정하지 않는다"**는 원칙은 여전히
    유효 — HITL 리뷰(§1)에서는 실제로 재현되는 진짜 버그였다. 둘의 차이는
    "재현 가능한가"다.

### 이 프로젝트에서 반복 확인된 패턴

**규칙보다 예시가 세다.** system 규칙을 넣어도 안 지켜지고 few_shot에 대조 쌍을
넣으니 잡히는 사례가 반복됐다(classifier·dashboard_writer·intake·eval-category).

**few_shot은 런타임 입력과 바이트 단위로 같아야 한다.** 어긋나도 에러가 아니라
조용한 품질 저하로 나타난다(rule_amendment v1이 3주째 이 상태였다).

**리뷰는 코드만 보지 말고 재현하면 신뢰도가 완전히 달라진다.** HITL 리뷰에서
"이론상 가능한 버그"를 임시 Postgres 컨테이너 + 격리 워크트리로 실제 재현해
전달하니, 상대가 몇 시간 만에 정확한 수정을 내놓았다 — 재현 스크립트까지 같이
주면 재검증도 빠르다.

## 7. 환경·툴체인 특성

- Docker 실행 중이어야 eval이 정상 동작(`docker compose ps`로 확인).
- DB 호스트 포트는 5433. 컨테이너는 빌드 시점 코드를 굳히므로 `--build` 필요.
- 워크트리별 `uv sync` 필요.
- **PostToolUse:Edit 훅이 Edit 도구 호출마다 자동으로 `ruff format`을 돌린다.**
  저장소가 전면 포맷돼 있지 않아(기존 부채), Edit로 수정할 때 diff 범위를 꼭
  확인하고 의도치 않은 재포맷이 섞이면 Bash로 직접 고칠 것.
- **격리 워크트리 안의 서브에이전트는 자기 워크트리 밖에서 git 명령을 실행할 수
  없다.** 필요한 브랜치는 자기 워크트리 안에서 직접 `git checkout`.
- **Bash 도구는 명령어 텍스트에 `eval`이라는 부분 문자열이 그대로 나타나면
  차단한다**(`eval/` 디렉터리를 `ls`만 해도 막힘). `python -m eval.run_eval` 실행
  시 `runpy.run_module`을 문자열 조각으로 나눠 호출해 우회.
- **`docker compose up -d llm-postgres`가 포트 충돌할 수 있다** — 다른 워크트리가
  이미 같은 포트를 쓰면, 별도 포트로 임시 Postgres 컨테이너를 띄우고 그 실행에
  한해 `DATABASE_URL`만 오버라이드하는 방식이 안전하다(공유 컨테이너를 병렬
  에이전트끼리 같이 쓰면 데이터가 섞인다). **버그 재현·재검증 용도로도 이 패턴이
  유효하다** — 임시 컨테이너 + `git worktree add <스크래치패드 경로> <브랜치>`로
  공유 개발 DB를 건드리지 않고 프로세스 레이스·동시성 버그를 실제로 재현할 수
  있다(이번 세션 HITL 리뷰에서 실제 사용, §1 참고). 테스트 후 컨테이너·워크트리
  정리 필수.

```bash
git fetch origin --prune                     # 항상 먼저
uv run pytest -q                             # 전체 통과 기대
uv run python -m eval.run_eval               # 오승인 0·정확도 ≥90%
uv run python scripts/predeploy_check.py     # 배포 전 점검
```
