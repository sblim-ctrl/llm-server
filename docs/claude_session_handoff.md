## 4. 🔴 새 세션이 가장 먼저 볼 것

### 4-1. cowbro와 sblim이 갈라져 있다

`7ec8d73`으로 `ba06b6c`(BIGINT)만 cherry-pick 해서 그 앞뒤의 팀장 작업분이 안 넘어왔다.
`git merge-tree` 드라이런 기준 **충돌 25건**이다.

**가장 위험한 것 — 같은 파일명에 다른 내용인 프롬프트 3건.**

| 파일 | cowbro | sblim |
|---|---|---|
| `adjudicator/v3` | 관리자 사유 수치 인용 강제 | 확장 입력 대응 + 임계값 일반화 |
| `digest_writer/v2` | 총무 코멘트(advice) 추가 | few_shot 자기모순 해소 |
| `policy_drafter/v2` | few_shot 3종 + 분량·문체 | few_shot 3종 + 금액 정책 명시 |

`adjudicator/v3`은 **양쪽 다 `DEFAULT_VERSIONS`에 승격**돼 있다. 같은 설정값이 다른
프롬프트를 가리키므로 머지하면 한쪽이 조용히 덮인다.

**sblim 쪽이 기반이어야 한다.** cowbro `adjudicate.py:53`은 소견의 `verdict`+`summary`만
보내는데 cowbro v3는 "근거 조항·수치·판례를 인용하라"고 지시한다 — 지킬 수 없는 규칙이다.
팀장이 `build_adjudication_user`로 해결해뒀다. 다만 cowbro v3의 두 문장(요청자용 수치
금지, 관리자용 결정적 수치 강제)은 sblim에 없으므로 이식해 v4로 만드는 안을 제안해뒀다.

**`nodes/rule_auditor.py` 충돌이 §6-1의 "회칙 미등록 팀 두 갈래 구현" 지점이다.**
cowbro에는 호출 지점이 3개(query_rewriter·기본 정책 조항·일반 회칙), sblim에는 1개다.
머지하면 팀장이 모르는 기본 정책 모드가 딸려 들어간다 — 심사 동작 변경이라 합의가 먼저다.

**judge 하네스는 cowbro에만 있다** (`app/eval_judge.py` 등 7파일). 그래서 팀장은 판정
정확도만 쟀고 사유 품질 편차를 볼 수단이 없었다. `default_policy/v1`·`query_rewriter/v1`도
cowbro 전용이라 삭제 대상이 아님을 확인해야 한다.

> 상세와 통합 순서: `docs/internal/프롬프트_브랜치_통합계획_2026-08-04.md`

### 4-2. 골든셋은 여전히 깨져 있다

`uv run python eval/run_eval.py`는 골든셋 검증까지 가지도 못하고 **`apply_schema()`에서**
죽는다. DB에 남은 문자열 ID 행 때문에 BIGINT 마이그레이션이 거부된다. 이번 세션 측정으로
`precedents` 1,020 · `jobs` 100 · `context_chunks` 47 · `proposals` 7 = 1,174행이었다.

`eval/` 스크립트 7개가 전부 `apply_schema()`를 부른다 — `run_eval_real.py`도 포함이라
**실모드 측정도 같은 벽에 막힌다.**

그 벽을 넘어도 두 번째 벽이 있다. `expenseId`·`organizationId`가 문자열이라 42건 전부
`AnalyzeRequest` 검증에서 걸린다. 목 규약이 ID에 데이터를 싣는 방식이기 때문이다.

**목 규약은 `expense_id` 하나가 아니다.** `organizationId`에도 단서가 넷 더 있다 —
`lowbudget`(예산), `noauto`(auto_approve), `noexpense`/`balanced`(지출 이력),
`club`/`study`/… (모임 유형). 지출 fixture만 만들면 절반만 풀린다.

**순서 주의**: `eval/golden/golden_v1.json`이 **머지 충돌 파일**이다. 브랜치 통합이
먼저다 — 먼저 갈아엎으면 그 작업이 통째로 충돌한다.

### 4-3. 우리가 보는 100%는 AI 품질이 아니다

목 모드에서 LLM 판정은 전부 고정값이다. 특히 `adjudicate`의 목 응답은 **확신도를 항상
0.95로 고정**한다(`adjudicate.py:33,38`). "확신 없으면 사람에게" 안전장치가 목 모드에서는
**한 번도 작동하지 않는다.**

그리고 **골든셋으로는 분류기를 A/B 할 수 없다.** 골든셋 42건의 카테고리가 카탈로그 안에
드는 게 0건이라 `classify_category.py:56`에서 즉시 반환되고 LLM이 호출되지 않는다.
카테고리를 9종으로 바꾸는 작업이 남아 있다(골든셋이 충돌 파일이라 통합 후에).

### 6-3. 마법사 2단계 — 화면과 코드가 다르다

실측으로 확인한 것이다.

- **화면의 금액 입력이 판정에 아무 영향을 안 준다.** 소액 5만이 고정이라
  `min(5만, 관리자값)`이 항상 5만이다. 10만/20만/30만 어느 걸 골라도 결과가 같다.
- **화면의 "중간 지출 → 대기/자동"에서 "자동"은 코드에 없다.** 3구간 개념 자체가 없고
  5만 초과는 전부 대기다.
- **경계가 1원 어긋난다.** 코드는 `> 한도`라 50,000원은 자동 승인인데 화면은 "미만"이다.

재현: `uv run python scripts/wizard_step2_matrix.py`

**제안은 화면을 코드에 맞추는 쪽이다** — 3구간을 지탱하려면 금액 가드레일을 걷어내야
하는데 그게 §6-1의 오승인 5건이다.

## 8. 규율 (지킬 것)

1. **프롬프트/판정 rubric 변경은 사용자와 함께 결정.** 버전을 지우지 않고 새로 만든다.
   **실측으로 재현된 개선만 승격.**
   - 예외적으로 `classifier/v3`은 실측 없이 승격했다 — v1이 존재하지 않는 라벨을
     가르치는 상태라 정합성 수정이었다. 골든셋이 살아나면 실측할 것.
   - **버전 번호를 sblim과 겹치지 않게 쓴다.** classifier가 v2를 건너뛴 이유다.
2. **머지 게이트**: `pytest` 전체 통과 + 골든셋 **오승인 0건**·정확도 ≥90%.
3. **AI는 승인/반려를 실행하지 않는다.** 추천만 콜백으로 보내고 실행·예산 차감은 백엔드.
4. **`.env`의 `MOCK_LLM=true`는 절대 바꾸지 말 것.** 실모드는 프로세스 주입으로만.
5. 커밋 시 **파일을 하나씩 지정**해 `git add` — `git add .`·`git add -A` 금지.
6. **팀장 브랜치·공유 문서를 임의로 고치지 않는다.** main 반영은 PR로.
7. **결함이라고 주장하기 전에 다른 브랜치를 먼저 본다.** `git log --all -- <파일>`,
   `git show origin/sblim:<파일>`. 이번 세션에 프롬프트 결함 7건을 "발견"했는데 대부분
   팀장이 이미 고쳐둔 것이었다. cherry-pick으로 일부만 가져온 리포에서 특히 자주 생긴다.
8. **작업 전 머지 충돌 영향을 확인한다.** `git merge-tree --write-tree HEAD origin/sblim`으로
   충돌 수가 늘지 않는지 본다. 충돌 파일(골든셋·`prompts.py` 등)은 통합 후에 손댄다.
