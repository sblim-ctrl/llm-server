# 골든셋 목 규약 재설계안

작성 2026-08-04 · 개발자 A(cowbro) · 팀장 검토 요청

BIGINT 전환 이후 골든셋이 돌지 않는다. 원인과 고칠 범위를 정리하고, 합의가 필요한
항목을 마지막에 모았다. 골든셋은 두 사람 공용 자산이라 혼자 정하지 않았다.

---

## 1. 지금 무슨 일이 벌어지고 있나

`uv run python eval/run_eval.py`는 골든셋 검증까지 가지도 못하고 그 앞에서 죽는다.
실제 실패 순서는 두 단계다.

**첫 번째 벽 — DB 마이그레이션 거부.** `apply_schema()`가 옛 문자열 ID 행을 발견하고
멈춘다. `schema.sql`의 안전 검사가 정상 작동한 결과다.

| 테이블 | 문자열 team_id 행 |
|---|---|
| `precedents` | 1,020 |
| `jobs` | 100 |
| `context_chunks` | 47 |
| `proposals` | 7 |

`eval/` 스크립트 7개가 모두 `apply_schema()`를 부른다. 실모드 측정
(`run_eval_real.py:88`)도 같은 벽에 막힌다. 골든셋만 고쳐서는 아무것도 못 돌린다.

**두 번째 벽 — 목 규약.** DB를 치우면 그 다음에 `AnalyzeRequest` 검증에서 42건이
전부 걸린다. `expenseId`·`organizationId`가 문자열이기 때문이다.

## 2. 목 규약은 expense_id 하나가 아니다

인수인계 문서에는 원인이 "expense_id에 지출 상세를 인코딩"으로만 적혀 있는데,
실제로는 `organizationId`에도 단서 네 개가 더 박혀 있다. 전부
`app/tools/backend_client.py`에 있다.

| 단서 | 하는 일 | 위치 |
|---|---|---|
| `?title=&amount=…` | 지출 상세 오버라이드 | `get_expense_detail:258` |
| `lowbudget` | 예산 잔액 1,000원 | `get_budget_status:84` |
| `noauto` | auto_approve 꺼짐 | `get_team_settings:290` |
| `noexpense` / `balanced` | 지출 이력 시나리오 | `get_expense_history:104,106` |
| `club`/`study`/`social`/`hobby`/`company` | 모임 유형 | `get_team_profile:325` |

골든셋 42건이 쓰는 organizationId 12종이 `golden-club-lowbudget`,
`golden-company-noauto-1` 같은 이름이라 전부 이 단서에 얹혀 있다. 지출 fixture만
만들면 절반만 풀린다.

## 3. 제안 — 파일로 옮긴다

지금 방식이 ID에 데이터를 실은 이유는 코드 주석에 적혀 있다. api와 worker가 별도
프로세스라 메모리 시딩으로는 전달이 안 되기 때문이다. 그 제약은 맞다. 다만 해법이
ID일 필요는 없다. 디스크의 파일은 두 프로세스가 똑같이 읽는다.

`eval/fixtures/mock_backend.json` 한 벌을 두고, `backend_client`의 목 분기가 이
파일을 조회한다. 경로는 `MOCK_BACKEND_FIXTURES` 환경변수로 덮어쓸 수 있게 한다
(팀장 골든셋 60건이 다른 파일을 쓰고 싶을 때를 위해).

```json
{
  "version": "1",
  "organizations": {
    "9002": {
      "label": "golden-club-lowbudget",
      "team_type": "동아리/학생회",
      "auto_approve": true,
      "budget": { "total_budget": 20000, "spent": 19000 },
      "expense_history": "default"
    }
  },
  "expenses": {
    "90001": {
      "title": "동아리 스터디 교재",
      "amount": 32000,
      "category": "도서",
      "date": "2026-07-01",
      "description": "알고리즘 스터디 교재 2권"
    }
  }
}
```

`expense_history`는 `default` / `none` / `balanced` 세 값으로 기존 `noexpense`·
`balanced` 규약을 대신한다.

숫자에는 의미를 담지 않는다. 9002가 "예산 부족 팀"인 이유는 번호가 아니라 fixture
파일이 그렇게 적어서다. 지금 실수를 숫자로 반복하지 않으려는 것이다. 사람이 읽을
이름은 `label`이 갖는다.

주의 — `eval/`은 Dockerfile 16행에서 이미지에 복사된다. fixture를 고치면 컨테이너를
다시 빌드해야 반영된다(인수인계 §7 함정 ①과 같은 함정).

## 5. 고쳐야 할 코드

목 분기 5곳이 본체다.

- `backend_client.get_expense_detail` — 쿼리 파싱 제거, fixture 조회
- `backend_client.get_budget_status` — `lowbudget` 제거
- `backend_client.get_team_settings` — `noauto` 제거
- `backend_client.get_expense_history` — `noexpense`/`balanced` 제거
- `backend_client.get_team_profile` — 유형 단서 제거

문서에 안 잡혀 있던 부수 수정이 여섯 곳 더 있다. 이게 이 작업의 실제 크기다.

- `eval/run_eval_real.py:65-66` — `DELETE … WHERE team_id LIKE 'golden-%'`. team_id가
  BIGINT가 되면 `LIKE`가 성립하지 않는다. 골든 팀 ID 목록으로 바꿔야 한다. 이건 실모드
  측정 전후의 판례 오염 청소라서 조용히 실패하면 측정 결과가 오염된다.
- `eval/run_eval_langsmith.py:99` — `golden-` 접두사 판정
- `tests/test_analyze_pull_model.py` — 67·79·84·89·100·115행이 문자열 ID를 쓴다
- `tests/test_eval_writers.py:52` — `get_expense_history("golden-club-1")`
- `app/static/dashboard.html` — `demo-team-1` 등 6곳
- `scripts/smoke_mcp.py:34` — `demo-team-1`

`tests/test_analyze_pull_model.py`는 지금 자기모순 상태다. 41행은 "문자열 ID는
거부한다"고 검증하는데, 67행 아래로는 문자열 ID로 목을 호출한다. 288개가 다 통과하는
이유는 `backend_client`가 `str(expense_id)`로 뭐든 받아주기 때문이다. 타입 계약이 API
경계에서만 지켜지고 그 아래는 아직 문자열로 말하고 있다.

## 6. 순서

```
0. DB 옛 행 정리                     팀장
1. fixture 파일 + backend_client 5곳  A
2. 골든셋 42건 ID 치환               A
3. 부수 6곳 수정, pytest 288 유지     A
4. 목 골든셋 재통과 확인             A
5. 실모드 측정 착수                  A
```

0번이 없으면 1~5가 전부 막힌다.

### 순서 정정 (2026-08-04 추가) — 브랜치 통합이 먼저다

이 문서를 쓴 뒤 cowbro와 sblim이 갈라져 있는 걸 발견했다
(`프롬프트_브랜치_통합계획_2026-08-04.md`). **`eval/golden/golden_v1.json`과
`writers_golden_v1.json`이 머지 충돌 파일이다.**

그러니 위 1~5번보다 브랜치 통합이 앞선다. 먼저 fixture로 갈아엎으면 머지 때 그
작업이 통째로 충돌하거나 날아간다. 팀장님 60건도 같은 파일 계열이라 두 번 일하게 된다.

한 가지 더. 골든셋 42건의 카테고리를 카탈로그와 대조해보니 **후보 안에 드는 게 0건**
이다(밖 40건, 나머지 2건은 카테고리 없음). 골든셋은 `도서`·`다과`·`홍보`를 쓰는데
카탈로그는 `교재/자료비`·`식비/다과비`·`홍보/콘텐츠비`다. `classify_category.py:56`이
후보 밖 카테고리면 LLM을 안 부르고 즉시 반환하므로, **골든셋으로는 classifier를 A/B
할 수 없다.** 팀장님도 같은 걸 확인하고(`classifier/v2` 헤더) 직접 호출 스모크로
우회했다.

fixture 재설계 때 ID만 숫자로 바꾸지 말고 카테고리도 카탈로그 값으로 맞춰야 한다.

여기서 한 가지 덧붙이면, 4번 목 골든셋 100%는 품질 지표가 아니다. 목 모드 판정은
`adjudicate.py:33,38`에서 확신도를 0.95로 고정한다. "확신 없으면 사람에게" 안전장치가
목 모드에서는 한 번도 작동하지 않는다는 뜻이다. 4번은 파이프라인 회귀 테스트로만
취급하고, 진짜 숫자는 5번에서 나온다. 1~4에 과투자하지 않으려 한다.

## 7. 팀장님 결정이 필요한 것

1. **DB 1,174행을 지워도 되는지.** `precedents` 1,020행이 걸린다.
   `run_eval_real.py` 주석대로면 과거 목 실행이 남긴 임베딩 찌꺼기로 보이는데,
   팀장님 작업분이 섞여 있을 수 있다. 지워도 되면 `TRUNCATE`로 정리하겠다.
   BIGINT가 팀장님 담당이라 실행은 그쪽에서 하시는 게 맞을 것 같다.
2. **fixture 파일 방식에 동의하시는지.** 반대하시면 대안은 목 백엔드를 별도
   프로세스로 띄우는 것인데, 규모가 훨씬 커진다.
3. **ID 대역.** 위 제안(cowbro 9001~/90001~, sblim 9100~/91000~)으로 괜찮은지.
4. **sblim 60건은 누가 옮길지.** 매핑 규칙만 맞추면 기계적인 작업이라 제가 같이
   해도 되고, 팀장님이 직접 하셔도 된다.
5. **파일 하나를 공유할지 두 개로 나눌지.** 공유하면 대역 충돌만 조심하면 되고,
   나누면 `MOCK_BACKEND_FIXTURES`로 각자 지정한다.

6. **브랜치 통합과의 순서.** 골든셋 파일이 머지 충돌 대상이라 통합이 먼저라고 본다.
   동의하시는지.

1번과 2번 답을 받으면 착수할 수 있다. 다만 6번 때문에 실제 착수는 브랜치 통합
이후가 될 것 같다. 3~5번은 진행하면서 맞춰도 된다.
