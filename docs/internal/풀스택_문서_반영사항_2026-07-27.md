## 1. 즉시 수정 확정 — 회신 불요 (3건)

문서가 값의 **의미**를 확정해 준 결과, 우리 코드가 명백히 틀린 상태가 된 항목이다. 풀스택 회신을 기다릴
필요가 없어 이번 커밋에서 함께 수정한다.

| # | 문서 근거 | 현행 코드 | 실연동 시 증상 |
|---|---|---|---|
| 1 | `team_settings.escalation_threshold BIGINT NOT NULL` — "에스컬레이션 상한액 / 이 금액 초과 시 무조건 관리자 검토" → 우리 `force_escalation_amount`와 1:1 | `load_context.py`가 이 값을 `confidence_threshold`(0~1 실수)에 대입. `force_escalation_amount`는 백엔드 값을 아예 읽지 않고 기본 300,000 고정 | `confidence_threshold = 300000.0` → `adjudicate.py`의 임계 비교가 상시 거짓 → **전건 에스컬레이션**. 목이 `0.8`을 반환하고 있어(`backend_client.py` `get_team_settings`) 지금까지 드러나지 않았다 |
| 2 | `team_settings.auto_approve_limit BIGINT NULL` — "자동 승인 사용 시에만 값 존재" (실서비스 기본은 `auto_approve=FALSE`이므로 NULL이 정상 케이스) | `int(settings_r.get("auto_approve_limit", 50_000))` — 키가 있고 값이 `None`이면 `TypeError` | load_context 예외 전파 → 워커 재시도 소진 → fail-safe 콜백. 안전 방향이긴 하나 **정상 처리 가능한 건이 전부 에스컬레이션**되고 로그가 오염된다 |
| 3 | `budgets.used_budget` (DB 컬럼) / API-026 응답 `usedBudget` | `budget_auditor.py`가 `budget["spent"]`를 참조 (`get_budget_status`의 목 응답 키에 맞춰져 있음) | 실모드 `KeyError: 'spent'` → BudgetAuditor 실패 → 가드레일 `auditor_failed:budget` → 에스컬레이션 |

**수정 방침**

- ①: `escalation_threshold` → `PolicyParams.force_escalation_amount`로 대입. `confidence_threshold`(θ)는
  Q4④ 합의대로 **LLM 내부 파라미터**로 남기고 백엔드 값에서 분리한다(기본 0.8 유지).
- ②: `None`이면 **0**으로 처리한다. 근거 — 설계서 §8 "어떤 실패도 자동 승인으로 이어지지 않는다".
  한도 0이면 모든 금액이 `over_auto_approve_limit`에 걸려 에스컬레이션되므로 안전 방향이다.
- ③: `backend_client.get_budget_status` **경계에서만** 흡수한다. `budget_auditor`·`budget_calculator`의
  내부 계약(`total_budget` / `spent`)은 유지 — 변경면을 최소화한다.
  단, 내부 Agent API가 미문서화라 응답 키가 `used_budget`(DB 표기)인지 `usedBudget`(프론트 API 표기)인지
  확정할 수 없어 **양쪽 키를 모두 수용**한다. 이 불확정 자체는 아래 §3-1에 회신 항목으로 올린다.

### 3-2. AI 심사 API의 동기/비동기 불일치

API-045 `POST /api/expenses/{expenseId}/ai-review`의 응답이 `success, review{finalVerdict, detail,
suggestedCategory, processedBy, createdAt}` — **즉답 형태**로 기술되어 있습니다. 그런데 우리 파이프라인은
`POST /v1/analyze` 202 수락 → 워커 그래프 실행 → 콜백이며, `expenses.ai_job_id` / `ai_dispatched_at`
(콜백 매칭·스케줄러 타임아웃 판단용) 컬럼의 존재도 비동기 전제입니다. 즉 **API-045가 응답하는 시점에는
아직 review가 없습니다.**

→ **확인 요청**: API-045는 "심사 요청 접수"만 하고 결과는 콜백으로 받는 구조가 맞는지(그렇다면 응답값 표기가
오류), 아니면 동기 즉답을 기대하시는지.

### 3-3. 카테고리 ENUM 충돌 — 교집합 0개 (우리 입장: ENUM 확장 요청)

| | 값 |
|---|---|
| DB `expenses.category` | `ENUM('회의','IT_인프라','행사','교육','식비','디자인','기타')` — 전역 7종, NOT NULL |
| 우리 `templates/category_catalog.yaml` | 모임 유형별 6종 × 5유형 = 30종 (`행사/프로그램비`·`교재/자료비`·`숙박/여행비`·`장비/용품비` …) |

겹치는 값이 하나도 없습니다. 우리가 내려보내는 `suggestedCategory`를 그대로 `expenses.category`에 넣으면
ENUM 위반으로 저장이 실패합니다(`expenses_reviews.suggested_category`는 VARCHAR(50)이라 저장 자체는 되지만,
관리자가 그 추천을 채택하는 순간 같은 문제가 발생합니다).

→ **우리 입장: ENUM 확장을 요청드립니다.** 근거는 값 목록 자체입니다. 현 7종은 회사형 지출에 치우쳐 있어
동아리·친목·동호회의 대표 지출(숙박·대관·교통·장비·홍보·다과)을 표현할 수 없고, 전부 '기타'로 몰립니다.
이는 "모임 유형별 서비스"라는 제품 전제와 충돌하고, 카테고리별 통계(API-048)의 해상도도 떨어뜨립니다.

확장 방식은 두 가지를 제안합니다 — ⓐ 5개 유형의 대표 카테고리를 합집합으로 ENUM에 추가, 또는
ⓑ `category`를 ENUM 대신 카테고리 테이블 FK로 전환해 유형별 카탈로그를 DB가 소유. 확장 전까지 우리
카탈로그는 현행 유지하며 코드를 바꾸지 않습니다.

### 3-4. Q1 미해소 — 등록 시점 자동 승인 (재제기)

API-016 비고가 여전히 "팀 설정의 autoApprove, autoApproveLimit 값에 따라 등록 시점의 status가
SUBMITTED / ESCALATED / **APPROVED** 중 하나로 자동 결정됨"입니다.

AI 심사 없이 등록 시점에 APPROVED가 되면 ① REQ-012 fail-safe("어떤 실패도 자동 승인으로 이어지지 않는다")
위배 ② AI 심사가 무력화 ③ 우리 `guardrail_gate`의 `auto_approve` 게이트와 이중 판정이 됩니다.

→ **확인 요청**: 등록 시점 status는 항상 SUBMITTED이고 APPROVED 전이는 콜백 수신 후에만 일어나는 것이
맞는지. (7/15 Q1의 재질의입니다)

### 3-5. Q4③ 미해소 — escalationThreshold를 수정할 API가 없음

`team_settings.escalation_threshold`는 DB에서 **NOT NULL**인데, API-028(팀 설정 조회)·API-029(팀 설정 수정)의
필드 목록에는 없습니다(API-009 응답 `settings`에만 등장). 관리자가 이 값을 조회하거나 변경할 수단이 없고,
모임 생성 시 값을 안 넣으면 NOT NULL 제약에 걸립니다.

→ **요청**: API-028/029 필드에 `escalationThreshold` 추가, 그리고 API-009에서 `settings`를 생략했을 때의
기본값 정의.

### 3-6. API-044 AI 정책 추천 — 요청·응답 모두 불일치

| | 요청 | 응답 |
|---|---|---|
| API-044 | `teamId` | `recommendedPolicies[{title, policyType, content}]` |
| 우리 `/v1/policy-draft` | `team_type`, `team_name`, `initial_budget`(필수, >0), `member_count`, `description` | `rules[]`, `policy_params{auto_approve_limit, force_escalation_amount, confidence_threshold}`, `recommended_categories[]`, `notes` |

세 가지 확인이 필요합니다.

1. 우리가 제안했던 무-teamId 호출(모임 유형 + 소개만 전달)은 반영되지 않고 `teamId` 기반이 유지됐습니다.
   마법사 1단계 시점에 teamId가 없다는 기존 문제가 어떻게 해결되는지(모임 생성 후 API-031로 별도 등록하는
   흐름으로 정리된 것인지) 확인 요청드립니다.
2. `policy_params` 추천(자동승인 한도 등)을 담을 응답 필드가 없습니다 — 폐기인지, API-029로 별도 반영하는지.
3. `teams.initial_budget` 컬럼이 DB에서 삭제됐는데(비고: "예산 테이블의 현재 예산으로") API-009 요청·응답에는
   `initial_budget`/`initialBudget`이 그대로 있습니다. 우리 `PolicyDraftRequest.initial_budget`은 필수값이라,
   API-044 호출 시 이 값을 어디서 조달하는지(budgets 조회) 확정이 필요합니다.

### 3-7. API-024 대시보드 AI 요약이 정식 등재됨 — 스코프 재결정 필요

`GET /api/teams/{teamId}/dashboard/ai-summary`가 **동기 GET + `summary` 문자열**로 등재됐습니다. 우리는 이
항목을 Sprint 2 스코프로 제외해 둔 상태이고, 현재 DigestWriter는 202 비동기 잡(`POST /v1/digests`)입니다.

→ **요청**: 백엔드가 집계 데이터를 넘기고 문구만 받는 방식이면 우리가 **집계 입력형 동기 엔드포인트**
(`POST /v1/digests/inline`)를 신설합니다. 요청에 실을 집계 필드 목록을 주시면 됩니다. 정산 리포트
요약(API-050)도 같은 패턴으로 갈지 함께 확정 요청드립니다.

### 3-8. 명세 자체 결함 2건

1. **`audit_logs.event_type` ENUM에 빈 항목** — `ENUM('AI_REVIEW_REQUESTED', , 'ESCALATED', 'APPROVED',
   'REJECTED', 'CANCELLED')`에 값이 비어 있는 자리가 있습니다. 또 비고는 "EDITED, ESCALATED 등"이라고 쓰여
   있는데 `EDITED`가 목록에 없고, **AI 심사 완료(소견 저장) 이벤트**도 없습니다 — 우리 콜백이 도착했을 때
   어떤 event_type으로 기록되는지 불명확합니다.
2. **`teams.initial_budget`** — DB에서는 삭제(비고에 삭제 논의 기록), API-009에는 잔존 (§3-6-3과 동일 건).

### 3-9. R5 미해소 — 알림에 AI 사유를 담을 수 없음

API-036 비고가 "notifications 테이블엔 user_id, expense_id만 저장되고, message는 조회 시점에 서버가
**expenses·users를 조인**해서 조립"이라고 명시합니다. Q2가 audit_logs로 해소되면서 AI 소견은 audit_logs에
있는데, 알림 조립 조인 대상에는 audit_logs가 없습니다.

→ **요청**: 에스컬레이션 알림(REQ-026·028)에 AI 보류 사유·불일치 항목을 담으려면 조립 조인에 audit_logs
추가가 필요합니다.

### 3-10. 정책 변경 훅 없음 + API-046 반환 규약 미확정

- API-031(정책 등록)·API-033(정책 수정) 시 우리 `POST /v1/context/refresh`를 호출해 줄 주체가 명세에
  없습니다. 재인덱싱이 트리거되지 않으면 RuleAuditor가 **옛 회칙으로 심사**합니다. `policies.version`이
  이미 있으므로 이벤트에 `{team_id, change_type: "rule", version}`만 실어 주시면 됩니다.
- API-046(AI 심사 결과 조회) 비고가 스스로 "status가 ESCALATED인 동안은 expenses_reviews에 데이터가 없어
  review가 비어있을 수 있음 (404 vs null 응답 처리 방식 확인 필요)"로 미확정 표기되어 있습니다.
  → **우리 제안**: 에스컬레이션 소견은 API-022(처리 이력)로 노출하고, API-046은 `review: null` 반환으로
  규약을 고정하는 것이 프론트 분기가 단순합니다.
