## 0. 전제 — 화면 4장 중 우리 소관은 엔드포인트 1개뿐

llm-server는 UI가 없다. 화면 4장은 전부 프론트 소관이고, 우리가 이 화면들에 기여하는 것은
`POST /v1/policy-draft` 하나다. (`app/static/dashboard.html`은 `/ui`로 열리는 **내부 데모·관측
전용**이며 마법사 화면이 아니다.)

| 화면 | 우리 코드 | 커버 범위 |
|---|---|---|
| 모임 생성 | `PolicyDraftRequest` — 이 화면 입력을 받는 형태로만 존재 | 유형·이름·예산·소개 ✅ / 20명 제한 ❌ |
| 마법사 1단계 (회비·예산) | `categories_for()` → `recommended_categories` | 카테고리 추천 ✅ / 회비 ❌ |
| 마법사 2단계 (승인 정책) | `PolicyParamsSuggestion` — 추천값 생성만, 저장은 백엔드 | 금액 2종 ✅ / `auto_approve` 토글 ❌ |
| 마법사 3단계 (회칙·규정) | `POST /v1/policy-draft` = "AI 초안" 버튼 | AI 초안 ✅ / 업로드·직접입력·건너뛰기 ❌ |

## 2. 화면에 있으나 우리 계약·코드에 없음 (6건)

전부 `docs/` 전문 grep 0건 기준이다.

### 2-1. 회비 금액 + "없음" 옵션 (1단계)

`회비`·`dues` 문서 전체 0건. `PolicyDraftRequest`의 금액 입력은 `initial_budget` 하나뿐인데,
이 필드는 **`Field(gt=0)` + required**(`writers.py:16`)라 "없음"을 표현할 구조 자체가 없다.

화면상 "초기 예산"(모임 생성)과 "회비 금액"(1단계)은 **별개 입력 2개**인데 우리는 하나만 받는다.
화면 설명이 *"AI가 예산 심사 시 기준으로 활용해요"*라 LLM이 쓰는 값으로 읽힌다.

> **LLM팀 결정(2026-07-29) — 반영 완료**: 회비는 **초안 생성 시에만** 사용한다.
> 심사(`budget_auditor`)에는 쓰지 않는다 — 심사에까지 쓰려면 내부 조회 API ③(예산 현황)에
> 회비 필드 추가를 요청해야 해서 범위가 커진다.
>
> 실제 사용처는 **회칙 조항 + notes 두 곳**이다(`policy_draft.py` `DUES_RULE`).
> **자동승인 한도 계산에는 넣지 않았다** — 회비는 1인당 금액인데 `member_count`가 선택값이라
> 총액으로 환산할 수 없고(2-2 참조), 총액 없이 회비를 한도 공식에 넣으려면 "한도 ≤ 1인 회비"
> 같은 **임의 정책을 새로 만들어야** 하기 때문이다. 관리자에게 보이는 숫자를 근거 없이 바꾸는
> 셈이라 보류했다. 필요하면 한 줄로 추가할 수 있다.

### 2-2. 무료 플랜 최대 20명

`플랜`·`무료`·`20명` 0건. 인원 관련 필드는 `member_count`(`writers.py:17`) 하나인데
**nullable·선택·상한 검증 없음**이고, `initial_budget`과 달리 제약이 전혀 붙어 있지 않다.

더 근본적인 문제: **모임 생성 화면에 인원 입력란이 없다.** 이 값의 조달 경로가 불명이다.
정원 검증(20명 상한)은 과금·플랜 개념이라 백엔드 소관으로 보는 것이 자연스럽다.

### 2-3. "당연히 모든 지출 직접 확인할래요" 토글 (2단계)

기능적 대응물은 `auto_approve`(bool, 기본 false)이며 가드레일 0번 규칙으로 이미 구현돼 있다
(`guardrail_gate.py`, `백엔드_요구_내부API_명세.md:51-54`). 문제는 **위치**다 —
이 값은 백엔드 `team-settings`에만 있고 우리 `PolicyParamsSuggestion`에는 없어서
(`writers.py:21-24`), **AI가 이 토글을 추천값으로 내려줄 수 없다.**

마법사 2단계가 이 토글을 설정하는 화면이므로, 값의 조회·저장 경로(API-028/029)가 함께 필요하다.
이는 기존 회신요청 5번과 같은 건이다.

### 2-4. 중간 구간(50,000~200,000원) "대기/자동" (2단계)

우리 모델은 임계값 2개(`auto_approve_limit`, `force_escalation_amount`)뿐이고 중간 구간의
별도 동작 정의가 없다. 실제로 이 구간을 가르는 것은 금액이 아니라 **confidence θ(기본 0.8,
`writers.py:24`)** 이다. 화면의 "대기/자동"이 그 뜻인지 확인이 필요하다.

### 2-5. 회칙 파일 업로드 / 직접 입력 (3단계)

`업로드`·`upload`·`직접 입력` 0건. 우리는 회칙을 **파일이 아니라 텍스트로, 그것도 백엔드에서
pull** 한다(내부 조회 API ⑤ — `백엔드_요구_내부API_명세.md:81-88`). 업로드·직접 입력 자체는
백엔드 API-031 소관이라 우리 계약에 없는 것이 정상이다.

**다만 치명적인 연결 고리가 비어 있다.** 등록 직후 `POST /v1/context/refresh`를 쏴 줄 주체가
아직 명세에 없다(회신요청 7번, 대기항목 R3 잔여). 이 알림이 없으면 **마법사 3단계에서 회칙을
등록해도 심사에 전혀 반영되지 않는다.** 마법사가 정식 화면으로 확정된 이상 7번의 긴급도가 올라간다.

### 2-6. "건너뛰기 → 기본 정책 모드" (3단계)

`기본 정책` 0건, `건너뛰` 1건이나 무관한 용례다(`업무분장_스프린트1_작업명세_v2.md:139` —
그래프가 adjudicate 노드를 건너뛰는 경로 설명). 회칙이 없는 상태에서 `rule_auditor`가 무엇을 근거로 심사하는지
정의가 없다. 우리 `templates/policy_templates.yaml`의 유형별 기본 조항을 적용한다는 뜻인지,
회칙 심사 자체를 건너뛴다는 뜻인지 화면만으로는 알 수 없다.

## 3. 값 불일치 (3건)

### 3-1. 고액 기준 — 화면 200,000원 vs 우리 산출값 300,000원 ⚠️ 산출식 문제

`policy_draft.py:100-105`의 실제 계산:

```python
auto_limit = max(10_000, (int(req.initial_budget * template["auto_approve_ratio"]) // 10000) * 10000)
params = PolicyParamsSuggestion(
    auto_approve_limit=auto_limit,
    force_escalation_amount=auto_limit * 6,
)
```

`auto_approve_ratio`는 유형별 0.03~0.06(`templates/policy_templates.yaml`). 화면의 소액 기준
50,000원이 나오려면 초기예산 100만원(× 0.05)이고, 그때 고액 기준은 **50,000 × 6 = 300,000원**이
되어 화면의 200,000원과 어긋난다.

즉 이것은 기본값 하나를 고치는 문제가 아니라 **배수 상수의 문제**다 — 화면 표
(소액 5만 미만 / 중간 5~20만 / 고액 20만 이상)가 성립하려면 배수가 **6이 아니라 4**여야 한다.

`app/schemas/common.py:58-59`의 기본값도 `50_000` / `300_000`으로 같은 6배 관계다.

> **LLM팀 결정(2026-07-29)**: **화면 기준 200,000원으로 정렬**한다 (배수 6 → 4).

### 3-2. 필수 표시 불일치

모임 생성 화면은 `*`(필수)가 **모임 유형에만** 붙어 있다. 그런데 우리 API는
`required: ["team_type", "team_name", "initial_budget"]`이고 `initial_budget`은 0 초과여야 한다.
화면대로 이름·예산을 비운 채 제출하면 **422**가 난다.

이는 `initial_budget` 조달 경로 미확정(회신요청 11번 ③ — `teams.initial_budget` 컬럼이 DB에서
삭제됨)과 같은 뿌리의 문제다.

### 3-3. `동아리/학생회` vs `동아리_학생회`

기존 미해결 건. 우리는 슬래시, 백엔드 DB ENUM은 언더스코어
(`풀스택_문서_반영사항_2026-07-27.md:209`). 화면 칩 라벨은 "동아리/학생회"(슬래시)라
**화면은 우리 표기와 일치**한다 — 백엔드 DB ENUM만 예외다.

## 5. 화면 설계 자체의 모순 (풀스택 확인 필요)

스텝퍼 라벨 순서가 화면마다 다르다.

| 화면 | 스텝 라벨 순서 | 본문 | 버튼 |
|---|---|---|---|
| 1단계 | 회비·예산 → **회칙·규정** → **승인 정책** | 회비와 예산을 설정해요 | 다음 |
| 2단계 | 회비·예산 → **승인 정책** → **회칙·규정** | 얼마부터 직접 확인하시겠어요? | 이전 / **설정 완료** |
| 3단계 | 회비·예산 → **회칙·규정** → **승인 정책**(활성) | **회칙·규정을 등록해 주세요** | 이전 / 건너뛰기 / **다음** |

2·3단계의 라벨 순서가 서로 뒤집혀 있고, 3단계는 활성 스텝 라벨("승인 정책")과 본문
("회칙·규정을 등록해 주세요")이 어긋난다. 게다가 **2단계에 "설정 완료", 3단계에 "다음"**이
붙어 있어 어느 쪽이 마지막 단계인지 상충한다.

우리 계약에는 영향이 없지만(마법사 단계 개념은 애초에 확정 문서에 없다), 회칙 등록 시점이
승인 정책 설정 전인지 후인지에 따라 `context/refresh` 발신 타이밍이 달라지므로 확인이 필요하다.

`auto_approve_limit < force_escalation_amount` 순서만 검사하므로 배수 변경에 영향받지 않는다.
심사 골든셋 30건 중 20만~30만원 구간 지출이 0건이라 기본값 변경으로 판정이 바뀌는 케이스도 없다.

> ⚠️ **`docs/openapi.json`은 전체 재생성하면 안 된다.** 이 파일은 **14경로 큐레이션본**인데
> 현재 브랜치의 앱은 `/v1/proposals/budget`(팀 결정 MVP 제외 — `백엔드_요구_내부API_명세.md` §5)을
> 아직 노출하고 있어, 통째로 덤프하면 15경로가 되어 제외 결정이 되살아난다.
> 갱신은 **변경된 스키마만 교체**하는 방식으로 해야 한다(포맷: `indent=2, sort_keys=True,
> ensure_ascii=False` + 끝 개행 — 이 설정으로 무손실 라운드트립됨을 확인). 참고로
> 그 문서가 언급하는 `scripts/dump_openapi.py`는 **실제로 존재하지 않는다.**
