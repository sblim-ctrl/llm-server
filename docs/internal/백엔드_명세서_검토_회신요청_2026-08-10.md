## §A. 확인·요청 사항 (14건)

### A-1. ★ 내부 에이전트 API가 명세서에 없습니다 — 섹션 추가 요청

API 명세서(API-001~052)는 프론트↔백엔드 API만 다루고 있고, 저희가 사용하는
**`/internal/agent/**` 내부 API 8종(BE-001~009)과 `POST /agent-callback` 수신
계약이 전부 빠져 있습니다.** 내부 API도 같은 문서(또는 별도 문서)에 실려야 서로
같은 것을 보며 대조할 수 있습니다.

→ 내부 API 섹션 추가를 요청드립니다. 기준 초안은 저희가 이미 드린
`docs/백엔드_요구_내부API_명세.md` §5 요약표를 그대로 쓰셔도 됩니다.

→ 아울러 **BE-007(멤버 명단)·BE-009(지출 이력) 미구현 2종의 구현 일정**도 함께
알려주시길 요청드립니다. 구현 전까지 PII 마스킹 미적용·4개 기능(대시보드 AI 요약,
정산 리포트, 주간 다이제스트, 예산 제안) 불가 상태가 계속됩니다(2026-08-10 회신
초안 ③·④에서 말씀드린 내용과 동일).

### A-2. ★ expenses.category ENUM이 구 7종입니다 — 9종 마이그레이션 반영 확인

테이블 스키마의 `expenses.category`가
`ENUM('회의','IT_인프라','행사','교육','식비','디자인','기타')` **구 7종**으로 되어
있습니다. 2026-08-04~05 합의로 확정된 **전역 9종**은 다음과 같습니다(저희
`templates/category_catalog.yaml` version 2, `GET /v1/categories` 응답과 동일):

> 식비 · 교통 · IT_인프라 · 교육 · 회의 · 장소_대관 · 행사_활동 · 비품 · 기타

이 상태로는 저희 콜백의 `suggestedCategory`가 신규 4종(교통·장소_대관·비품·
행사_활동)일 때 ENUM에 값이 없어 **저장이 실패**합니다. 8/10 회신에서 "DB
마이그레이션은 AWS 배포와 함께"라고 하셨으니 문서만 구판일 가능성이 높다고
보고 있습니다.

→ ① 9종 마이그레이션이 배포에 포함되는지 재확인, ② 스키마 문서도 9종으로 갱신
요청드립니다. ('행사'→'행사_활동' 대체와 '디자인' 삭제 여부도 문서에서 확인이
안 됩니다.)

### A-3. ★ expenses.category가 NOT NULL입니다 — "등록 시 null" 합의와 충돌

기존 확정 계약(BE-001, 2026-08-06)은 **"지출 등록 시 category는 null, 저희 콜백의
suggestedCategory로 채운다"** 였고, 실제로 API-016(지출 등록) 요청 필드에도
category가 없습니다. 그런데 스키마에는 `category ... NOT NULL`로 되어 있습니다.

→ 어느 쪽이 맞는지 확인 부탁드립니다.
- NULL 허용이 맞다면: 스키마 문서 수정만 하면 됩니다.
- NOT NULL 유지라면: 등록 시점에 무슨 값을 넣으시는지(예: '기타'), 그리고 BE-001
  지출 상세 응답에서 저희가 **"아직 미분류"를 어떻게 구분**하는지 규약이
  필요합니다. ('기타'가 기본값이면 저희 분류기가 "이미 분류된 지출"로 오인해
  분류를 건너뛸 수 있습니다 — 저희는 category가 비어 있을 때만 분류합니다.)

### A-4. ★ 지출 일자(date) 컬럼이 없습니다 — 영수증 날짜 대조 기준 확인

expenses 테이블에 날짜 관련 컬럼이 `createdAt`(등록 시각)뿐입니다. 그런데:

- BE-001(지출 상세)·BE-009(지출 이력) 합의 응답에는 `date`(지출 일자, YYYY-MM-DD)가
  있습니다.
- 저희 증빙 심사는 **영수증에 찍힌 날짜 ↔ 청구된 지출 일자**를 대조해 불일치
  (`mismatch: date`)를 잡습니다.

`date` = `createdAt`의 날짜 부분이라면, "어제 결제하고 오늘 등록"한 정상 건이
전부 날짜 불일치로 잡히는 문제가 생깁니다(등록 시각은 지출 시각이 아니므로).

→ ① 지출 일자 컬럼(예: `expense_date DATE`)을 신설해 등록 폼에서 받으실지,
② `date = createdAt::date` 규약으로 갈지 확정 부탁드립니다. ②라면 저희가 날짜
불일치 판정 기준을 완화(예: 영수증 날짜 ≤ 등록일 허용)하는 협의가 이어져야 합니다.

### A-5. ★ 에스컬레이션 심사 결과 저장 정책이 문서 안에서 서로 다릅니다

같은 주제에 대해 지금 4개의 서로 다른 서술이 있습니다:

| 출처 | 내용 |
|---|---|
| 테이블 스키마(expenses_reviews 머리말) | "에스컬레이션일 경우 해당 테이블 저장 x → 최종 결과만 저장" |
| 같은 표의 final_verdict ENUM | `('APPROVED','REJECTED','ESCALATED')` — **ESCALATED가 있음** |
| 2026-08-10 백엔드 회신 | "final_verdict에 escalate 저장 가능" |
| API-046 설명 | "status가 ESCALATED인 동안은 expenses_reviews에 아직 데이터가 없어 review가 비어있을 수 있음" |

저희가 이걸 중요하게 여기는 이유: **에스컬레이션 콜백에는 관리자가 판단할 근거
(감사관 소견 `opinions[]`, 관리자용 사유 `reasons.admin`)가 실려 있습니다.** 이게
어디에도 저장되지 않으면 관리자는 "확인 필요"라는 사실만 보고 **왜 확인이 필요한지
를 못 봅니다.** (저희가 최근 요청자용/관리자용 에스컬레이션 문구를 분리·정비한
것도 이 노출을 전제로 한 작업이었습니다.)

→ 에스컬레이션 시점 콜백의 소견·사유가 **어느 테이블에 저장되고 어느 API로
노출되는지**(expenses_reviews에 ESCALATED 행으로? audit_logs.detail로?) 확정
부탁드립니다.

### A-6. 지출 등록~AI 심사 흐름이 동기처럼 읽힙니다 — 비동기 확인

- API-045(AI 지출 심사)가 응답으로 `review: { finalVerdict, ... }`를 **바로
  돌려주는 동기 API처럼** 기술되어 있습니다.
- API-016(지출 등록)은 "팀 설정에 따라 **등록 시점의 status가** SUBMITTED /
  ESCALATED / APPROVED 중 하나로 **자동 결정"** 이라고 되어 있습니다.

저희 심사 API(`POST /v1/analyze`)는 **202 접수 후 콜백**으로 결과를 드리는 비동기
구조입니다(LLM 심사는 수 초~수십 초 걸립니다). 등록 트랜잭션 안에서 심사 결과를
기다리는 구조라면 전면 재협의가 필요합니다.

→ ① 등록 시 status=SUBMITTED로 두고, 심사 콜백 도착 시 APPROVED/ESCALATED로
전이하는 흐름이 맞는지 확인 부탁드립니다(그렇다면 API-016·045 설명만 다듬으면
됩니다). ② 그리고 **autoApprove=false인 팀도 심사 요청은 보내주시는지** 확인
부탁드립니다 — 합의된 설계는 "심사·소견은 항상 생성, 자동 실행만 차단"이라
꺼진 팀도 관리자 화면에 AI 소견은 보여야 합니다.

### A-7. processed_by 값: 'HUMAN' vs 저희 콜백 'ADMIN'

스키마의 `expenses.processed_by`·`expenses_reviews.processed_by`는
`ENUM('AI','HUMAN')`인데, 저희 콜백 `processedBy`는 `"AI" | "ADMIN" | null`
(에스컬레이션은 null)로 합의돼 있습니다(`docs/풀스택_연동_계약.md` §3 배지
규칙표).

→ 콜백의 'ADMIN'을 백엔드가 'HUMAN'으로 매핑해 저장하시는지, 아니면 저희가
와이어 값을 'HUMAN'으로 바꿔야 하는지 확정 부탁드립니다. (한쪽이 한 줄 고치면
되는 문제라 방향만 정하면 됩니다.)

### A-8. verdict 표기: 콜백 소문자 현재형 vs DB 대문자 과거형 (기존 FQ2 잔여)

저희 콜백 `verdict`는 `approve | reject | escalate`(소문자)이고, DB
`final_verdict`는 `('APPROVED','REJECTED','ESCALATED')`(대문자)입니다. 저장값이
대문자인 것은 이번 스키마로 확인됐으니, **와이어(콜백 본문) 값을 누가 변환하는지**만
남았습니다.

→ 콜백은 현행 소문자 그대로 두고 백엔드가 저장 시 변환하시는지 확인 부탁드립니다.
(변경이 필요하면 저희 쪽 한 줄 수정으로 대응 가능하나, 골든셋·테스트 갱신이 함께
움직여야 해서 확정 후 일괄 반영을 원합니다.)

### A-9. expenses_reviews.detail(JSON 1필드)에 무엇이 어떻게 들어가나요 (기존 FQ6)

저희 콜백에는 `opinions[]`(감사관 4종 소견) · `mismatch[]`(증빙 불일치) ·
`reasons{requester, admin}`(요청자용/관리자용 사유 분리)가 실립니다. 스키마의
`expenses_reviews.detail`은 JSON 1필드입니다.

→ ① 콜백의 어느 필드들이 detail에 어떤 구조로 저장되는지, ② API-046(지출 상세
심사 결과 — **요청자도 조회**)과 API-022(처리 이력)의 detail에 **관리자용 사유
(`reasons.admin`)가 요청자에게 노출되지 않는지** 확인 부탁드립니다. 요청자용·
관리자용 문구를 분리해 드리는 이유가 노출 범위 차이 때문입니다.

### A-10. 회칙 "팀당 1건" 전제 확인 — policies 테이블 구조와 어긋납니다

2026-08-07 합의는 **"회칙은 팀당 1개, 덮어쓰기 관리"** 였고, 저희는 이를 전제로
회칙 판번호(version)를 저희 쪽에서 자체 발급하도록 구현했습니다. 그런데:

- policies 테이블에 `UNIQUE(team_id)` 제약이 없고,
- API-030이 회칙 **목록**을 반환하며, API-031로 계속 **추가 등록**이 가능한
  구조입니다.

→ ① 팀당 여러 회칙이 실제로 허용되는지, 허용된다면 BE-005
(`GET /internal/agent/teams/{teamId}/policy-document?doc_type=rule`)는 **어느
건을 반환**하는지(최신 1건? 전체 병합?) 확정 부탁드립니다.
② 그리고 BE-005의 `doc_type`(rule/category 구분)이 policies의 어느 컬럼과
대응하는지도 알려주세요 — 현재 스키마에는 대응 컬럼이 없습니다
(`policy_type`은 TEXT/FILE 저장 방식 구분이라 다른 축입니다).

### A-11. 회칙 등록·수정·삭제 시 저희 재인덱싱 호출이 명세에 없습니다

API-031(등록)·033(수정)·034(삭제) 설명에 저희 **`POST /v1/context/refresh`**
(`{"team_id": ..., "change_type": "rule"}`) 호출이 언급돼 있지 않습니다. 이 호출이
없으면 저희 심사는 **바뀌기 전 회칙**으로 계속 심사합니다(저희는 회칙 원문을
백엔드에서 받아 인덱싱해 두고 심사 시 그걸 봅니다).

→ 회칙 변경 3종(등록/수정/삭제) 성공 시 `/v1/context/refresh`를 호출하는 것으로
명세에 추가 부탁드립니다. (팀 설정(API-029) 변경은 호출 불필요 — 설정값은 심사
때마다 실시간 조회합니다.)

### A-12. API-052가 참조하는 `/v1/budget-insights`는 존재하지 않는 경로입니다

API-052(AI 예산 관리 추천) 설명에 "내부적으로 LLM-016(`/v1/budget-insights`)
호출"이라고 되어 있는데, 저희 서버에 그 경로는 없습니다. **LLM-016의 실제 계약**
(`docs/풀스택_연동_계약.md` "LLM-016" 항목)은:

1. `POST /v1/proposals/budget` `{team_id, period?}` → **202 잡 접수** (동기 아님)
2. 완료 후 `GET /v1/proposals?team_id=&type=budget` 으로 결과 조회
3. 결과 payload 필드는 `category_analysis` · `budget_status_analysis` ·
   `recommendation` (snake_case — API-052의 camelCase 표기와 다름)

→ API-052 설명을 실제 계약(202 잡 + 조회)으로 정정 부탁드립니다. "캐시해두고
반환" 전략 자체는 좋습니다 — 잡 완료 후 결과를 캐시하시면 됩니다. 만약 **동기
1회 호출형이 꼭 필요**하시면 별도 협의를 요청드립니다(대시보드 요약처럼 동기
엔드포인트 신설은 가능하지만 LLM 지연이 페이지 로드에 직결됩니다).

### A-13. 관리자 승인/반려 결정이 저희에게 전달되는 경로가 없습니다 (BE-008)

API-019(승인)·020(반려)에 저희 쪽 통지가 없고, 결정 내역 조회용 내부 API도
명세에 없습니다. 관리자 결정이 저희에게 와야 **판례로 저장되어 다음 심사부터
반영**됩니다(같은 유형 지출의 반복 질의 감소, 반복 번복 감지). 지금 구조로는
관리자가 아무리 결정해도 AI가 학습하지 못합니다.

→ 방향 확정을 요청드립니다. 두 안 중 하나입니다:
- **push**: API-019/020 처리 성공 시 백엔드가 저희 `POST /v1/precedents`를 호출
  (저희 쪽 준비 완료, 즉시 가능)
- **pull**: 저희가 `GET /internal/agent/decisions?after_id=&limit=` 커서 폴링
  (설계서 v1.2 개정안 제안 — 백엔드 신규 API 필요, 응답에 `is_override`
  (AI 판단과 다른 결정 여부)가 필요한데 현 스키마에 원천 컬럼이 없어 산출 방식
  협의 필요)

### A-14. 영수증 파일 접근 API가 명세에 없습니다 (BE-004)

기존 확정은 "전용 API 없이 `GET /api/files/{fileName}` 재사용"이었는데, 이번
명세서에 `/api/files` 항목 자체가 없습니다. 스키마의 `expenses.receipt_url
VARCHAR(500)` 형식도 미정입니다.

→ ① 파일 조회 API를 명세에 추가하고(인증: 저희 Agent 토큰 허용 여부 포함),
② `receipt_url`에 저장되는 값이 **상대 경로**(`/api/files/abc.jpg`)인지 절대
URL인지, ③ 그 값이 심사 요청의 `receiptPath`에 **그대로** 담겨 오는지 확정
부탁드립니다. 절대 URL이라면 저희 HTTP 클라이언트가 그 호스트로 직접 나가면서
**Agent 토큰이 백엔드 밖으로 새는 구조**가 되어 상대 경로를 강하게 권장합니다.
(2026-08-10 회신 초안 ②와 같은 주제 — 함께 정리되면 좋겠습니다.)

## §B. 참고 전달 (3건 — 회신 불필요, 인지만)

**B-1. 알림에 에스컬레이션 유형이 없습니다.** `notifications.type`이
`('APPROVAL_REQUEST','APPROVED','REJECTED')`뿐이라, AI가 관리자 확인으로 넘긴
순간("확인 필요") 관리자에게 갈 알림 유형이 없습니다. 프론트/백 소관이지만 흐름상
공백으로 보여 전달드립니다.

**B-2. audit_logs.event_type ENUM에 빈 슬롯이 있습니다.**
`ENUM('AI_REVIEW_REQUESTED', , 'ESCALATED', ...)` — 오타로 보입니다. 아울러 기존
질의(2026-08-07 연동 계약 §3-2-1)였던 "AI 심사 완료(자동 승인/반려)에 대응하는
event_type" 이 여전히 없습니다. APPROVED/REJECTED + actor_type='AI' 조합으로
표현하시는 것이라면 그렇게만 알려주세요.

**B-3. 심사 타임아웃 값·늦은 콜백 규칙이 아직 미정입니다.**
`expenses.ai_dispatched_at`(스케줄러 타임아웃 판단용)으로 감시 메커니즘이 생긴
것은 확인했습니다. 다만 **타임아웃 값**(저희 제안 90~120초 vs 풀스택 초안 30초 —
LLM 심사는 30초를 넘을 수 있습니다)과 **타임아웃 후 도착한 콜백 처리 규칙**(무시?
소견만 저장?)은 여전히 미확정입니다. 배포 전 확정을 요청드립니다.
