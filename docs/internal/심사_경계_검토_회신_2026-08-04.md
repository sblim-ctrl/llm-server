## 개발자 A께 — 먼저 볼 세 가지 🔴

**① cowbro CI가 지금 빨간불입니다. 그리고 lint를 고쳐도 다음에서 또 멈춥니다.**

오늘 cowbro CI(run `30868610779`)는 **lint(ruff)** 단계에서 실패했고, 그 뒤 pytest·골든셋
스텝은 아예 실행되지 않았습니다. lint를 고치면 다음은 골든셋 게이트인데, 거기서
**BIGINT 크래시**가 납니다 (아래 E1). cowbro의 `analyze.py`도 `BigIntId`를 쓰고 cowbro
골든셋 42건도 문자열 ID인 것은 확인했습니다. lint만 고치고 초록불을 기대하지 마세요.

**② `rule_version`이 1로 못박혀 있어, 새로 만드신 `/v1/context/status`와 어긋납니다.**

`GET /v1/context/status`는 `MAX(version)`을 보고하는데(`app/db/pool.py`),
`load_context.py:38`은 여전히 `rule_version: 1` 하드코딩입니다. 화면은 "v2 반영됨"이라
말하는데 심사는 v1 조항으로 돕니다 (아래 E3). 기본 정책 모드와 같은 자리에서 걸리는
문제라 함께 보셔야 합니다.

**③ `query_rewriter`를 기본 정책 모드와 분리해 주실 수 있을까요.**

`rule_auditor.py` 변경에 **기본 정책 모드**와 **질의 재작성(gpt-4o-mini)** 두 기능이 함께

따로 보면 각각 판단하기 쉬울 것 같습니다.

## 2. 실제로 터지는 것 — 치명 4건, 주의 3건

각 항목의 **확인** 줄에 직접 실행해 관측한 것인지, 근거에서 도출한 예측인지 구분했습니다.

### E1 🔴 머지 게이트가 7월 30일부터 실행되지 않고 있습니다

`uv run python -m eval.run_eval`이 첫 케이스에서 `ValidationError`로 죽습니다. 골든셋
60건을 전수 검증하니 **통과 0건 / 실패 60건**입니다.

원인은 제 커밋 `ba06b6c`("BIGINT 식별자 타입 통일")입니다. `AnalyzeRequest`의
`expenseId`·`organizationId`를 `BigIntId`(strict 양의 정수)로 바꿨는데, 골든셋 목 규약은
`"golden-club-1"`·`"g-club-001?title=…&amount=…"` 같은 문자열입니다. `seed_demo`는 같은
이유로 이미 전환됐는데(`df28746`) 골든셋만 빠졌습니다.

- **근거**: `app/schemas/ids.py` · `app/schemas/analyze.py:27-28` · `app/eval_support.py:22`
- **확인**: 관측 — `run_eval` → exit 1. 60건 전수 `model_validate` → 0/60
- **영향**: CLAUDE.md가 정의한 머지 게이트("오승인 0건·정확도 ≥90%")가 5일간 무효.
  `pytest`는 203 passed라 아무도 못 느낍니다
- **결정 필요**: 골든셋을 숫자 ID로 전환하고, 목 규약(제목·금액을 `expenseId` 쿼리로 싣던
  방식)을 다른 채널로 옮겨야 합니다. 42/60 통합(E5)과 한 번에 처리하는 편이 낫습니다

### E2 🔴 CI가 이 파손을 볼 수 없는 구조입니다

`sblim`의 `.github/workflows/ci.yml`은 트리거가 `push: main` + `pull_request: main`뿐이라,
sblim 브랜치에 아무리 푸시해도 CI가 돌지 않습니다. E1이 닷새 묻힌 이유입니다.

더 볼 것은 **CI 정의 자체가 브랜치마다 다르다**는 점입니다. cowbro는
`push: [main, cowbro, sblim]`에 lint·OpenAPI drift 스텝까지 있습니다.

- **확인**: 관측 — lint 실패, 후속 4스텝 미실행 / 예측 — lint 수정 후 골든셋에서 E1과
  동일 크래시
- **결정 필요**: CI 트리거·스텝 정의를 어느 쪽으로 통일할지. lint를 게이트에 넣을지는
  CLAUDE.md 게이트 정의와도 얽힙니다

### E3 🔴 화면은 "v2 반영됨"이라 말하는데 심사는 v1로 돕니다

cowbro가 새로 만든 `GET /v1/context/status`는 `MAX(version)`을 보고합니다. 그런데
**cowbro의 `load_context.py:38`도 여전히 `rule_version: 1` 하드코딩**이고,
`search_rules`는 `WHERE version = %s` 정확 매칭에 `active` 필터가 없습니다.

회칙을 v2로 개정한 팀은 구버전 행이 삭제되지 않으므로 **심사가 영원히 v1 조항으로**
돕니다. 반대로 첫 인덱싱이 v≠1로 들어오면 0행 → `no_rules` → **회칙이 있는데도 기본 정책
모드로 오분류**됩니다.

- **근거**: `load_context.py:38` · `app/tools/search_rules.py` ·
  `app/graphs/indexing/nodes/upsert.py` · cowbro `app/db/pool.py`
- **확인**: 관측 — 세 파일의 버전 취급이 서로 어긋나는 것을 코드로 대조
- **수정 훅은 이미 있습니다**: `get_context_status`와 같은 조회를 `load_context`에서 한 번
  해 `rule_version`에 넣으면 §4.4 판정 일관성(심사 중 버전 고정)도 그대로 유지됩니다

### E4 🔴 실키 전환 시 LLM 판정이 게이트 결정을 넘어설 수 있습니다

`route_after_guardrail`(`guardrail_gate.py:95-97`)은 `proceed`와 `reject_candidate`를
구분하지 않고 둘 다 `adjudicate`로 보내고, `adjudicate.py:94`는 LLM verdict를
`gate_result`와 대조 없이 채택합니다. **잔액 부족 건에 실모드 LLM이 `approve`를 내면 그대로
전파됩니다.** §8 "어떤 실패도 자동 승인으로 이어지지 않는다"와 어긋나는 방향입니다.

8/3 문서 §5③의 "AI가 반려할 수 있는 건 예산 부족뿐"은 **목 모드 관찰**입니다 — 게이트를
존중하는 것은 `_mock_result`(`adjudicate.py:62-77`)뿐이고 코드 계약이 아닙니다. 그래서
**골든셋으로는 원리적으로 잡히지 않습니다.** 논의사항 3·4번의 전제가 여기 걸려 있습니다.

- **확인**: 관측 — 분기 코드에 대조 로직 부재. `tests/test_adjudicate.py`는 user 메시지
  빌더만 검증하고 verdict 채택 테스트 0건
- **수정**: `reject_candidate`인데 `approve`가 나오면 `escalate`로 강등하는 한 줄 + 테스트.
  전파 채널은 브랜치마다 다르지만(sblim은 API 직접 호출, cowbro는 `5eafa20`으로 콜백
  단일화) 위험은 동일합니다

### E5 🟡 브랜치 발산이 8/3 문서 §6이 서술한 것보다 훨씬 넓습니다

### E6 🟡 최후 안전장치가 죽을 수 있는 경로

잡은 `expense_id`를 갖고 있어 발생 확률은 낮지만, 하필 §8의 최후 방어선이라 정리 가치가

### E7 🟡 "골든셋 42/42 통과"가 기본 정책 모드를 보증하지 않습니다

골든 팀은 전부 회칙 미인덱싱 상태이고(`app/tools/backend_client.py`의 목 회칙 주석이 이를

그래서 기본 정책 모드를 머지하면 42건 전부가 그 경로를 타는데, 목 응답이 `pass` 고정이라

어느 안을 택하든 이 경로의 테스트 신설이 먼저입니다.

## 3. 논의사항 7건 — 권고

8/3 문서 §7의 표를 그대로 따르되 권고와 근거를 붙였습니다. 결정은 함께 하는 것으로.

**1. 회칙 없는 팀 심사 — (b)를 보되, E3 해결과 `query_rewriter` 분리 전에는 머지하지 않기**

(b) 실물은 예상보다 좋습니다. 반려 불가를 프롬프트가 아니라 **코드로 강제**하고
(`fail`→`warn` 강등), 금액 조항은 템플릿 placeholder 유무로 정확히 걸러내며, 근거에
"등록된 회칙 아님"을 명시합니다. 금액 조항을 뺀 이유("그 팀이 동의한 적 없는 금액")도
타당합니다.

다만 E3·E7이 함께 걸려 있고, **선택지가 둘이 아니라 셋**입니다 — **(c) 백엔드가 유형별 기본
조항을 v1 정책으로 저장·인덱싱**하는 안이 이미 우리 문서에 있습니다
(`docs/풀스택_팀별_AI에이전트_연동제안.md:228-232`, `docs/풀스택_회신요청.md:395`).
(c)는 근거 출처가 팀 DB가 되어 화면에서 조항 원문을 인용할 수 있고 LLM 서버는 무수정이라
구조적으로 낫지만, 회신 15⑥ 미회신 + `get_policy_document` 엔드포인트 미확정 +
R3(이벤트 주체) 미정이라 지금 결정할 수 없습니다.
**(b)로 화면 약속을 먼저 지키고 (c) 확정 시 이관**이 현실적입니다.

**2. 한도 초과 건을 AI에 맡길지 — 현행 유지. 정확히는 "아직 결정할 수 없음"**

"5건은 최악값" 논리는 맞습니다. 다만 뒤집으면 **실제값을 아무도 모른다**는 뜻입니다.
확신도 안전장치는 0.95 고정 탓에 한 번도 작동한 적이 없으니, C를 여는 것은 미검증 전제에
전부를 거는 결정입니다. 순서에 0단계를 더합니다 —
**E1 복구 → 42/60 통합 → 실키 확신도 분포 측정**. 그다음이 원칙 → 골든셋 → 코드입니다.

**3. 확신도 기준 — 2번 종속**

θ는 현재 팀별 설정이 불가능한 구조입니다(`load_context.py:71` 주석 — 백엔드가 모르는 LLM
내부 파라미터라 분리 유지). "금액 건만 0.9로"는 `PolicyParams` 필드 추가가 아니라
`adjudicate`의 조건부 임계값 로직 신설이 필요합니다.

**4. 회칙 위반도 AI가 반려? — 유지. 단 E4 강제 장치와 세트로**

이유(코드가 계산한 뺄셈 vs LLM이 해석한 조항)에 동의합니다. 근거를 하나 더하면,
`rule_auditor`는 근거를 못 찾으면 `warn`, 인덱스가 없으면 `pass`로 빠지므로 `fail`은
"검색이 성공했고 + LLM이 위반으로 읽었다"의 합성입니다. 검색 품질이 반려 신뢰도를
좌우하는데 실측이 아직 부분적입니다(`rule_auditor.py:27-30`).

유지로 정하더라도 E4 때문에 **실키에서는 코드가 그 결정을 강제하지 않습니다.** 관리자
부담은 반려 권한이 아니라 콜백에 조항 원문·판례를 실어 **1클릭 반려를 돕는 쪽**으로 더는
게 낫습니다(회신 16③과 이어집니다).

**5. 절대 상한 — 유지**

안 걸리는 이유는 **기본값 관계(5만 < 20만)** 이지 설계 결함이 아닙니다. 관리자가 한도를
20만 넘게 잡는 순간 유일한 상한이 되므로, 없애면 그 경우 상한이 사라집니다.

함께 정리할 것 — 백엔드에 `auto_approve_limit ≤ escalation_threshold` 저장 검증 요청
(`app/graphs/writers/policy_draft.py:164-165`엔 이미 있으나 `team_settings` 저장 경로엔
없습니다), 회신 16⑦ 배수 충돌(마법사 4배 vs 예산관리 5배)과 묶어 처리.

**6. 마법사 구간표 — 2번을 기다리지 말 것 (이번 커밋에서 정정 완료)**

**7. 5만원 경계 — 화면 문구를 "미만"에서 "이하"로**
