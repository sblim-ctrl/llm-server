# cowbro · sblim 통합 계획

작성 2026-08-04 · 개발자 A(cowbro) · 팀장 검토 요청

AI 품질 트랙(인수인계 §5-③)을 시작하려고 프롬프트를 조사하다가 두 브랜치가 크게
갈라져 있는 걸 발견했다. 프롬프트 개선은 통합 이후로 미룬다 — 지금은 어느 쪽 기준으로
A/B를 해도 결과가 반쪽이다.

작업 트리는 건드리지 않았다. 아래 충돌 목록은 `git merge-tree` 드라이런 결과이고,
코드 변경은 없다(`pytest` 288개 통과 유지).

---

## 1. 어쩌다 갈라졌나

`7ec8d73`으로 sblim의 `ba06b6c`(BIGINT)만 cherry-pick 했다. 그 앞뒤의 프롬프트
작업분(`79d42c5` "프롬프트 11종 신버전", `38708ad` "precedent_auditor v3 승격" 등)은
안 넘어왔다. 공통 조상은 `bbd9bb7`이고 미머지 커밋이 20개 이상이다.

양방향이라 fast-forward가 아니다.

| | 프롬프트 |
|---|---|
| sblim에만 | `classifier/v2`, `precedent_auditor/v2`·`v3`, `rule_auditor/v4`, `intake/v2`, `budget_planner/v2`, `rule_amendment/v2`, `briefing_writer/v1`·`v2`, `report_writer/v1`·`v2` |
| cowbro에만 | `judge/v1`·`v2`·`v3`, `default_policy/v1`, `query_rewriter/v1` |
| 같은 이름, 다른 내용 | `adjudicator/v3`, `digest_writer/v2`, `policy_drafter/v2` |

인수인계 §4-3 "승격 이력 없는 프롬프트 7종"은 cowbro만 본 서술이라 낡았다. sblim에서는
`classifier`·`intake`·`precedent_auditor`가 이미 승격됐다.

## 2. 머지하면 충돌 25건

`git merge-tree --write-tree HEAD origin/sblim` 실측이다.

| 갈래 | 파일 |
|---|---|
| 프롬프트 (add/add) | `adjudicator/v3`, `digest_writer/v2`, `policy_drafter/v2` |
| 코드 | `api/context.py`, `nodes/callback.py`, `nodes/rule_auditor.py`, `review/state.py`, `llm/prompts.py`, `middleware/auth.py`, `schemas/analyze.py`, `schemas/callback.py` |
| 골든셋 | `golden_v1.json`, `writers_golden_v1.json` |
| 테스트 | `test_analyze_pull_model.py`, `test_auth_middleware.py`, `test_callback.py`, `test_prompts.py` |
| 기타 | `ci.yml`, `smoke_review.py`, 문서 6건(`.docx` 포함) |

골든셋 2건이 충돌 목록에 있다는 게 중요하다. **`골든셋_목_규약_재설계안`의 fixture
작업과 이 머지는 같은 파일을 건드린다.** 순서를 정하지 않으면 한쪽 작업이 날아간다.

### `nodes/rule_auditor.py` 충돌의 정체

이 파일이 인수인계 §6-1이 경고한 "회칙 미등록 팀 처리가 이미 두 갈래로 구현" 지점이다.

cowbro의 `rule_auditor.py`에는 LLM 호출 지점이 3개다.

- 61행 `query_rewriter` (CRAG 재작성기)
- 120행 기본 정책 조항 — "등록된 회칙 아님, 유형별 기본값"
- 163행 일반 회칙 조항

sblim에는 84행 하나뿐이다. **머지하면 팀장님이 모르는 기본 정책 모드가 딸려 들어간다.**
이건 프롬프트 문제가 아니라 심사 동작 변경이라, 코드보다 합의가 먼저다.

## 3. 프롬프트 충돌 3건

### 3-1. `adjudicator/v3` — 양쪽 다 승격, 내용이 다름

양쪽 `DEFAULT_VERSIONS`가 둘 다 `"adjudicator": "v3"`이다. 같은 설정값이 브랜치마다
다른 프롬프트를 가리킨다.

| | 무엇을 고쳤나 |
|---|---|
| cowbro v3 (07-22) | 관리자용 사유에 결정적 근거 수치를 숫자로 인용하도록 강제. 요청자용은 수치 금지 명시 |
| sblim v3 (07-24) | 확장 입력(근거 조항·수치·판례 블록) 대응. confidence 하드코딩 0.8을 팀별 임계값 참조로 일반화 |

**sblim 쪽이 기반이 되어야 한다.** cowbro의 `adjudicate.py:53`은 소견을 이렇게만 보낸다.

```python
user="\n".join(f"[{k}] {v.verdict}: {v.summary}" for k, v in opinions.items()),
```

`verdict`와 `summary`뿐이다. 그런데 cowbro v3의 규칙은 "근거 조항·수치·판례를 포함해
구체적으로"다. `Opinion.evidence`(회칙 원문)와 `similar_cases`(판례)는 전달되지 않으니
**모델이 지킬 수 없는 규칙**이다. 팀장님의 `build_adjudication_user`가 이걸 해결한다.

다만 cowbro v3의 두 문장은 sblim에 없다.

- 요청자용: `(반려 시에도 "예산 잔액이 부족하여"처럼 숫자 없이 성격만 전한다.)`
- 관리자용: `결정적 근거가 된 핵심 수치는 반드시 숫자로 인용하라 — "예산 부족" 같은
  요약만으로는 불충분하다.`

sblim v3의 관리자용 규칙은 방향이 반대다. "입력에 없는 조항·수치·판례를 만들어 쓰는
것은 금지"로 **환각 방지**에 초점이 있고, cowbro는 **누락 방지**다. 상충이 아니라
보완이다.

**제안: sblim v3 기반 + cowbro 두 문장 이식 = `v4` 신설.** 양쪽 v3는 지우지 않는다.

### 3-2. `digest_writer/v2` — cowbro 예시가 검증기를 통과 못 한다

cowbro는 v2를 승격했고, sblim은 `DEFAULT_VERSIONS`에 `digest_writer`가 없어 v1로
동작한다(sblim v2는 미승격 초안).

cowbro `digest_writer/v2`의 few_shot 2건을 `verify_digest_pure`에 직접 넣어봤다.

```
예시 1: verify_digest_pure = True    누락 없음
예시 2: verify_digest_pure = False   누락 토큰: ['284,000원']
```

예시 2의 `projected_period_end_spent`가 284,000원인데 summary·highlights 어디에도 그
수치가 없다. 검증기는 이 토큰을 요구한다(`digest.py:303`). **모범 예시를 충실히
모방할수록 `verified=false`로 강등된다.**

sblim v2 헤더가 지목한 누락 토큰은 "반려 0건"으로 다르지만 같은 예시(2번)의 같은 종류
결함이다. 팀장님이 고친 방식을 그대로 가져오면 된다.

곁가지로 few_shot의 `forecast` 블록이 실제 `BurnForecast` 스키마와 다르다 —
`elapsed_days`·`over_categories`·`under_categories`가 빠져 있다.

### 3-3. `policy_drafter/v2`

| cowbro | sblim |
|---|---|
| few_shot 3종 + 분량·문체 지침 | few_shot 3종(참고문서 기반) + 금액 정책 상호 명시, 빈 목록 반환 시연 |

서로 다른 문제를 같은 버전 칸에서 고쳤다. 둘 다 타당해 합치는 게 맞다. sblim도 미승격
초안이라 급하지 않다.

## 4. cowbro 프롬프트의 공통 결함

조사하다 보니 개별 사고가 아니라 계열이었다. **cowbro의 few_shot은 런타임이 실제로
보내는 형식과 다르다.** 손으로 쓰고 실제 직렬화 결과와 대조하지 않은 탓이다.

`rule_auditor/v3`(cowbro 승격본)을 실제 직렬화와 비교했다.

```
런타임:  {"title":"회식비","amount":120000,"category":"식비","date":"2026-07-03","description":"..."}
few_shot: {"title": "회식비", "amount": 120000, "category": "식비", "description": "..."}
```

차이 3가지 — ① `model_dump_json()`은 공백 없는 compact 직렬화인데 few_shot은 공백이
있다 ② `date` 필드가 few_shot에 없다 ③ 런타임은 JSON과 헤더 사이에 빈 줄(`\n\n`)이
있는데 few_shot에는 없다.

같은 계열이 이만큼 나왔다.

| 프롬프트 | 증상 |
|---|---|
| `rule_auditor/v3` | few_shot input이 런타임 직렬화와 불일치 (위 3가지) |
| `digest_writer/v2` | 예시 2가 자체 검증기 불통과 |
| `adjudicator/v3` | 입력에 없는 조항·판례를 인용하라고 지시 |
| `precedent_auditor/v1` | 입력에 없는 `decided_by`로 판정하라고 지시 |

팀장님은 이 계열을 `rule_auditor/v4` ②("런타임 user 메시지 형식에 정합화 — compact
직렬화 + date 필드 + 빈 줄, `rule_auditor.py:84`와 바이트 일치"), `precedent_auditor/v2`,
`adjudicator/v3`에서 체계적으로 고쳤다.

## 5. 반드시 가져와야 할 것 — `precedent_auditor/v3`

cowbro에는 `precedent_auditor` v1밖에 없다. **v2를 건너뛰고 v3로 가야 한다.**

v2는 "중복·분할 청구 검사는 결정주체와 무관 — 이미 승인된 지출 사실 자체가 근거"라는
규칙 때문에 카테고리·금액대만 같으면(정기 회식·정기 다과·정기 구독처럼 정당한 반복
지출까지) 전부 중복으로 취급했다. 실측에서 **정확도 100.0% → 61.7%로 붕괴**(23건,
대부분 승인 기대 건이 보류로).

v3는 "동일 사안 식별 기준"을 넣어 정기 반복과 재청구를 구분한다. 헤더에 데이터 계약
조사까지 적혀 있다 — `precedents` 테이블에 원 지출 날짜가 없고(`created_at`은 판정
시각) `_precedent_lines` 표기에도 날짜가 없어서, 날짜 인접성 대신 제목·설명 내용으로
동일 사안을 판단하도록 설계했다.

v3는 `_precedent_lines` 표기에 의존하므로 **노드 코드와 함께** 와야 한다.

## 6. `rule_auditor/v4`는 미승격이 맞다

v3 100% = v4 100% 동률이라 팀장님이 v3를 유지했다. 그 판단이 맞다.

다만 v4의 변경 ②(few_shot 형식 정합화)는 cowbro v3에 없는 수정이다. 통합 후에도 v3를
쓸 거라면 **그 부분만이라도 v3에 반영**하는 게 좋겠다. 지금 cowbro v3는 §4에서 본
형식 불일치를 그대로 갖고 있다.

## 7. judge 하네스는 cowbro에만 있다

```
app/eval_judge.py · eval/run_eval_judge.py · eval/compare_judge.py
prompts/judge/v1·v2·v3 · tests/test_eval_judge.py
```

sblim에는 judge 관련 파일이 하나도 없다. 이게 두 브랜치가 서로 다른 걸 본 이유다.

팀장님의 adjudicator 실측 기록은 "v2 100.0% = v3 100.0% 동률"로 **판정 정확도만** 잰
것이다. cowbro v3가 태어난 근거는 "가끔 '예산 부족'처럼 모호하게 나오는 편차
(LLM-as-Judge가 감지 — 관리자근거 불충분)"다.

판정은 맞는데 사유가 부실한 경우는 정확도로 안 잡힌다. judge가 있어야 보인다. 팀장님은
그 도구가 없어 사유 편차를 못 봤고, 나는 입력 계약이 깨진 걸 못 봤다. 합치면 둘 다 보인다.

`default_policy/v1`(회칙 미등록 팀)과 `query_rewriter/v1`(CRAG 재작성기)도 cowbro
전용이다. 통합 시 삭제 대상이 아님을 확인해야 한다.

## 8. 통합 순서 제안

```
0. default_policy 동작 합의        ← 인수인계 §6-1, 코드보다 먼저
1. judge·query_rewriter 인지 확인   ← 삭제 대상 아님
2. 프롬프트 충돌 3건 결정
     adjudicator     : sblim v3 기반 + cowbro 두 문장 → v4 신설
     digest_writer   : sblim 수정 반영 → v3 신설
     policy_drafter  : 양쪽 병합 → v3 신설
3. 머지 (DEFAULT_VERSIONS는 양쪽 승격분 합집합)
4. precedent_auditor v3 + 노드 코드 동반 확인
5. 골든셋 목 규약 재설계 (DB 정리 선행)
6. 실측으로 신설 버전 검증 → 승격
```

2번을 건너뛰고 머지하면 세 프롬프트 중 하나가 조용히 사라진다.
5번을 3번보다 먼저 하면 골든셋 충돌로 작업이 겹친다 — **머지가 먼저다.**

## 9. 팀장님 확인 사항

1. **`default_policy` 동작 변경.** 회칙 미등록 팀 처리가 cowbro `rule_auditor.py`에
   기본 정책 모드로 들어가 있다. 머지하면 심사 동작이 바뀐다. 이것부터 합의가 필요하다.
2. **`adjudicator/v3` 충돌.** sblim 기반 + cowbro 두 문장 이식으로 v4를 만드는 방향에
   동의하시는지.
3. **judge 하네스를 아시는지.** sblim에 없는 게 의도인지 분기 때문인지. 사유 품질은
   판정 정확도로 안 잡혀서 이 도구가 필요하다.
4. **`digest_writer` 병합.** cowbro 예시 2가 검증기를 통과하지 못한다(§3-2). sblim에서
   고치신 방식을 가져오면 되는지.
5. **`rule_auditor/v3` 형식 정합화.** v4의 ②만 v3에 반영해도 되는지.
6. **머지 방향과 순서.** sblim을 cowbro로 가져올지, 양쪽 다 main으로 PR을 낼지.
   골든셋 재설계는 머지 이후로 미루는 데 동의하시는지.

## 10. 이번에 되돌린 것

`precedent_auditor`의 판례 입력에 `decided_by`가 빠진 걸 결함으로 보고 고쳤다가
되돌렸다. 팀장님이 `79d42c5`에서 `_precedent_lines`로 이미 해결해뒀고, 빈 목록을
`(없음)`으로 처리하는 것까지 더 낫다. 같은 일을 두 방식으로 하면 머지 충돌만 남는다.
