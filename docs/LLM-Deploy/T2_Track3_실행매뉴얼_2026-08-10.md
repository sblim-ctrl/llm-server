## Part 1. T2 — Agent 토큰(역방향) 합의 (지금 바로 가능, 배포 대기와 무관)

배경: LLM→백엔드 호출(콜백·내부 조회 API)을 백엔드가 검증할 토큰이다. 코드는 이미 이
값을 `BACKEND_SERVICE_TOKEN`이라는 별도 필드로 받도록 분리해 뒀다(T1, 커밋 `b67a643`).
원래 계획은 우리가 생성해 전달하는 것이었으나, 백엔드가 2026-08-10 회신에서 **"현재
설정한 값을 비공개 채널로 공유할 테니 그대로 쓰거나, 우리가 정해서 알려달라"**고 제안했다
→ **백엔드 값을 그대로 수용**하기로 결정(백엔드 재배포 없이 가장 빠름).

### 1-1. 값 수신·품질 확인

비공개 채널로 값을 받으면 아래 3가지를 확인한 뒤 "그 값으로 쓰겠다"고 통보한다:

1. **기본값류가 아닐 것** — `dev-…-change-me` 같은 플레이스홀더나 짧은 단어면 거절
2. **기존에 전달한 `SERVICE_TOKEN`(백엔드→우리 방향)과 다른 값일 것** — 재사용 금지
3. **충분히 랜덤할 것** — 32자 이상 무작위 문자열 수준

셋 중 하나라도 걸리면 우리가 생성해서 역제안한다:

```bash
openssl rand -hex 32   # 64자 16진 문자열 — 이 값을 보안 채널로 전달
```

### 1-2. 값 취급 규칙

- **보안 채널로만** 주고받는다(다이렉트 메시지, 사내 시크릿 공유 도구 등). Slack 공개
  채널·이메일 평문·이 저장소의 어떤 파일이나 커밋에도 값 자체를 남기지 않는다.
- `docs/internal/백엔드_회신_초안_2026-08-10.md` ①번 항목이 "공유해 주시는 값을 그대로
  쓰겠다"는 안내만 담고 있다 — 그 문서에 값을 붙이지 않는다.

### 1-3. 어디에 쓰이는가

- 배포 VM의 `.env`에 `BACKEND_SERVICE_TOKEN=<받은 값>`으로 넣는다 (Part 2의 2-3에서 사용).
- **로컬 개발 저장소의 `.env`는 건드리지 않는다** — 로컬은 `MOCK_BACKEND=true`라 이 값이
  쓰이지 않는다(규율 4).

## Part 2. Track 3 — 백엔드 전달값 수신 후

**시작 조건**: ① base URL은 수신됨 — `https://bravobudget.duckdns.org` (HTTPS 재통보
2026-08-10. 같은 IP `54.180.206.27`로 resolve·Let's Encrypt 인증서 정상 확인).
② **검증용 지출 ID만 대기 중**(백엔드가 배포 DB에 데이터 생성 후 전달 예정. 팀 ID는
`1`로 확정). 지출 ID가 없어도 §2-1~2-3까지는 진행할 수 있다.

### 2-1. 우리 쪽 GCP 외부 IP 고정 확인 (Part 1과 별개로 지금 먼저 해도 됨)

백엔드는 이미 `34.50.39.240:8000`으로 나간다고 회신해 왔다 — 주소 전달은 끝난 셈이고,
**이 주소가 바뀌지 않게 고정**하는 것만 남았다.

1. GCP 콘솔 → **VPC 네트워크 → IP 주소**에서 배포 VM의 외부 IP(`34.50.39.240`)가
   "고정"인지 확인한다. "임시"로 되어 있으면 그 줄의 **"고정 주소로 승격"**을 눌러
   전환한다(이후 VM을 재시작해도 주소가 바뀌지 않는다).
2. 만에 하나 승격 과정에서 주소가 달라지면 백엔드에 즉시 알린다 — 백엔드 아웃바운드가
   이 주소를 바라본다(`docs/internal/백엔드_회신_초안_2026-08-10.md` ⑥번 항목).

### 2-2. 배포 VM 방화벽 규칙 추가 — 백엔드가 우리를 호출하도록 허용

GCP 콘솔에서 (SSH 아님):

1. 검색창에 `방화벽` → **`방화벽 규칙 만들기`**
2. 아래대로 채운다:

   | 항목 | 값 |
   |---|---|
   | 이름 | `allow-llm-from-backend` |
   | 대상 | 네트워크의 모든 인스턴스 |
   | 소스 IPv4 범위 | `54.180.206.27/32` — 백엔드 고정 IP (2026-08-10 수신) |
   | 프로토콜/포트 | TCP, `8000` |

3. **`0.0.0.0/0`은 절대 넣지 않는다** — 인터넷 전체에 여는 것이다.

(전체 절차는 `docs/LLM-Deploy/배포_실행순서_2026-08-07.md` §6-2와 동일하다 — 백엔드가
AWS로 확정되어 이제 "경우 A/B" 구분 없이 이 절차 하나만 있다.)

### 2-3. 배포 VM 코드·`.env` 갱신

2026-08-10 main에 커밋 20개가 머지됐다(토큰 분리 `b67a643`, 프롬프트 v4·v5 승격, 워커
안정화 등). `.env`만 고치지 말고 **코드 최신화와 묶어서 한 번에** 반영한다.

VM에 SSH 접속 후:

```bash
cd ~/llm-server

# 1) 잡 큐 확인 — running이 있으면 끝날 때까지 대기 (재빌드 중 워커 재시작으로 잡이 끊긴다)
docker compose exec llm-postgres psql -U budgetops -d budgetops_llm \
  -c "SELECT status, count(*) FROM jobs WHERE status IN ('queued','running') GROUP BY status;"

# 2) 롤백 대비 — 현재 커밋 기록해 두기
git log --oneline -1

# 3) 코드 받기 (docker-compose.yml 로컬 수정과 충돌하면: git stash && git pull && git stash pop)
git pull
```

`.env`를 열어(`nano .env`) 아래 두 줄을 채운다:

```
BACKEND_BASE_URL=https://bravobudget.duckdns.org
BACKEND_SERVICE_TOKEN=<Part 1에서 합의한 값>
```

- base URL은 HTTPS(443)라 포트 표기가 필요 없다. 반드시 `https://`로 시작한다 —
  `http://`로 넣으면 301 리다이렉트가 떠서 호출이 실패한다. 백엔드 통보값 끝에 붙은
  `/`는 떼고 넣는다.
- 나머지는 이미 설정돼 있어야 정상이다: `MOCK_LLM=false`·`MOCK_BACKEND=false`·
  `SERVICE_TOKEN`(기본값 아님)·`OPENAI_API_KEY`.

저장(`Ctrl+O` → `Enter` → `Ctrl+X`) 후 **재빌드+재생성을 한 번에** 한다 — `restart`가 아니다.
`.env`는 컨테이너를 **만들 때**만 읽히고 `get_settings()`가 `lru_cache`라, `restart`로는
반영되지 않는다(배포_실행순서 §6-1과 동일한 주의).

```bash
docker compose up -d --build --force-recreate llm-api llm-worker

docker compose ps                                            # 3개 컨테이너 전부 Up
docker compose exec llm-api printenv BACKEND_BASE_URL        # 반영됐는지 눈으로 확인
docker compose exec llm-api printenv BACKEND_SERVICE_TOKEN   # 반영 확인 — 화면에 값이 뜨니 주변에 안 보이게 주의
curl localhost:8000/healthz
curl "localhost:8000/readyz?deep=true"                       # 200이어야 함
```

### 2-4. 계약 검증 스크립트 실행

2-3에서 코드를 최신화했다면 그대로 실행한다. (§2-3을 건너뛰었다면 `git log --oneline -1`로
커밋 `b67a643` 이후인지 먼저 확인 — 그 전 코드에는 `BACKEND_SERVICE_TOKEN` 필드가 없다.)

```bash
docker compose exec llm-api python -m scripts.verify_backend_contract \
  --team-id 1 --expense-id <백엔드에게 받은 지출 ID>
```

(`--base-url`·`--token` 생략 시 `.env`의 `BACKEND_BASE_URL`·`BACKEND_SERVICE_TOKEN`을
자동으로 쓴다. `python scripts/verify_backend_contract.py`처럼 파일 경로로 직접
실행하면 **`ModuleNotFoundError: No module named 'app'`**가 난다 — Dockerfile이
`uv sync --no-install-project`라 `app`이 컨테이너에 패키지로 설치돼 있지 않고,
스크립트 경로 실행은 `scripts/` 디렉터리만 `sys.path`에 잡기 때문이다. 반드시
`-m scripts.verify_backend_contract` 모듈 방식으로 실행한다 — 2026-08-10 실측 확인.)

읽는 법:

- **CRITICAL 실패**(지출 상세·team_settings)면 **여기서 멈춘다** — 이 상태로는 심사가
  시작되지 않는다. camelCase 힌트가 뜨면 백엔드에 필드명 정정을 요청한다.
- **BE-007(멤버명단)·BE-009(지출이력) 관련 DEGRADED는 정상**이다 — 미구현이 이미
  확정된 항목이니 실패로 놀라지 않는다.
- 그 외 DEGRADED는 자동 처리율이 떨어진다는 신호일 뿐 배포를 막는 것은 아니다.
- **전 구간 401이 뜨면** — 2026-08-10 실측·원인 확정: `.env`도 백엔드(nginx)도
  아니라 **낡은 이미지**였다. `--force-recreate`는 기존 이미지로 컨테이너만 다시
  만들 뿐이라 `git pull` 후에도 `--build` 없이는 코드가 반영되지 않는다. 토큰 분리
  (`b67a643`) 이전 구코드는 `backend_service_token` 필드가 없어 내부 API 호출이
  `SERVICE_TOKEN`(반대 방향 값)으로 폴백 → 전 구간 401. 판별법 두 가지: ① 파이썬
  트레이스백·에러의 행 번호나 요청 파라미터가 현재 저장소 코드와 어긋나면 구코드다
  (실측: 구코드는 회칙 요청에 `version=1`을 붙였다). ② 토큰을 코드에 직접 박은
  단건 호출은 200인데 스크립트는 401이면 스크립트가 다른 토큰을 쓰고 있는 것.
  해결: `docker compose up -d --build --force-recreate llm-api llm-worker` 후 재검증.
  (2026-08-10 이 방법으로 해소 — 재빌드 후 CRITICAL 0건 통과.)
- **반대 방향(백엔드→우리, `SERVICE_TOKEN`)도 401이 날 수 있다** — 2026-08-10
  실측: 백엔드가 `POST /v1/dashboard/summary` 호출 시 401 보고. 우리 서버가 그
  토큰을 실제로 받아들이는지는 컨테이너 안에서 직접 재현해 확인한다(이미지에
  `curl` 없음 — `python:3.12-slim-bookworm` 베이스라 httpx로 대체):
  ```bash
  docker compose exec llm-api python -c "import os, httpx; \
    r = httpx.post('http://localhost:8000/v1/dashboard/summary', \
    headers={'Authorization': 'Bearer ' + os.environ['SERVICE_TOKEN']}, json={}); \
    print(r.status_code)"
  ```
  401이 아니라 **422**(빈 본문 검증 에러)가 나오면 인증은 통과한 것 — 우리 쪽
  문제가 아니라 백엔드 쪽 요청 헤더 형식(대소문자·공백·줄바꿈 혼입)을 의심한다.

### 2-5. 신규 카테고리 4종 콜백 저장 확인

교통·장소_대관·비품·행사_활동 중 하나로 실제 지출을 심사시켜 콜백이 백엔드에 정상
저장되는지 확인한다.

- 백엔드가 2026-08-10 회신에서 **카테고리 9종(언더바 표기) 반영 완료**라고 알려왔다 —
  이 단계는 확인 차원이다. 그래도 저장이 실패하면 우리 쪽 결함으로 단정하지 말고
  백엔드에 ENUM 마이그레이션 적용 여부부터 확인한다(기존 합의).

### 2-6. 실연동 E2E 1건

1. `POST /v1/analyze`로 실지출 1건 심사를 요청한다.
2. 워커 로그에서 `job … succeeded`를 확인한다.
3. 콜백이 2xx로 갔는지 확인한다(워커 로그 또는 `GET /v1/jobs/{job_id}`).
4. **백엔드 화면에서 그 지출의 상태가 실제로 바뀌었는지** 눈으로 확인한다 — 여기까지
   되면 실연동 완료다.
