## Part 1. T2 — 역방향 토큰 생성·전달 (지금 바로 가능, 배포 대기와 무관)

배경: 백엔드가 LLM→백엔드 호출(내부 조회 API)을 검증할 토큰 값을 우리가 정해서 달라고
요청했다(2026-08-10 회신). 코드는 이미 이 값을 `BACKEND_SERVICE_TOKEN`이라는 별도
필드로 받도록 분리해 뒀다(T1, 커밋 `b67a643`).

### 1-1. 값 생성

```bash
openssl rand -hex 32
```

64자 16진 문자열이 나온다. 이 값이 `BACKEND_SERVICE_TOKEN`이다. 기존에 전달한
`SERVICE_TOKEN`(백엔드→우리 방향)과는 **다른 값이어야 한다** — 재사용 금지.

### 1-2. 전달

- **보안 채널로만** 전달한다(다이렉트 메시지, 사내 시크릿 공유 도구 등). Slack 공개
  채널·이메일 평문·이 저장소의 어떤 파일이나 커밋에도 값 자체를 남기지 않는다.
- `docs/internal/백엔드_회신_초안_2026-08-10.md` ①번 항목이 "값은 별도로 전달하겠다"는
  안내만 담고 있다 — 그 문서를 보낼 때 이 값은 같이 붙이지 말고 별도 채널로 보낸다.

### 1-3. 어디에 쓰이는가

- 배포 VM의 `.env`에 `BACKEND_SERVICE_TOKEN=<생성한 값>`으로 넣는다 (Part 2의 2-3에서 사용).
- **로컬 개발 저장소의 `.env`는 건드리지 않는다** — 로컬은 `MOCK_BACKEND=true`라 이 값이
  쓰이지 않는다(규율 4).

## Part 2. Track 3 — 백엔드 전달값 수신 후

**시작 조건**: 백엔드로부터 ① Elastic IP 기반 base URL, ② 검증용 지출 ID를 받아야 한다
(검증용 팀 ID는 `1`로 이미 확정됨).

### 2-1. 우리 쪽 GCP 외부 IP 확정·전달 (Part 1과 별개로 지금 먼저 해도 됨)

1. GCP 콘솔 → **VPC 네트워크 → IP 주소**에서 배포 VM의 외부 IP가 "고정"인지 확인한다.
   "임시"로 되어 있으면 그 줄의 **"고정 주소로 승격"**을 눌러 전환한다(이후 VM을
   재시작해도 주소가 바뀌지 않는다).
2. 이 고정 IP를 백엔드에 전달한다 — 백엔드 쪽에도 아웃바운드 방화벽이 있다면 우리를
   화이트리스트해야 할 수 있다(`docs/internal/백엔드_회신_초안_2026-08-10.md` ⑥번 항목).

### 2-2. 배포 VM 방화벽 규칙 추가 — 백엔드가 우리를 호출하도록 허용

GCP 콘솔에서 (SSH 아님):

1. 검색창에 `방화벽` → **`방화벽 규칙 만들기`**
2. 아래대로 채운다:

   | 항목 | 값 |
   |---|---|
   | 이름 | `allow-llm-from-backend` |
   | 대상 | 네트워크의 모든 인스턴스 |
   | 소스 IPv4 범위 | 백엔드에게 받은 Elastic IP + `/32` (예: `52.78.x.x/32`) |
   | 프로토콜/포트 | TCP, `8000` |

3. **`0.0.0.0/0`은 절대 넣지 않는다** — 인터넷 전체에 여는 것이다.

(전체 절차는 `docs/LLM-Deploy/배포_실행순서_2026-08-07.md` §6-2와 동일하다 — 백엔드가
AWS로 확정되어 이제 "경우 A/B" 구분 없이 이 절차 하나만 있다.)

### 2-3. 배포 VM `.env` 갱신

VM에 SSH 접속 후:

```bash
cd ~/llm-server
nano .env
```

아래 두 줄을 채운다:

```
BACKEND_BASE_URL=<백엔드에게 받은 Elastic IP 기반 주소>
BACKEND_SERVICE_TOKEN=<Part 1에서 생성해 전달한 값>
```

저장(`Ctrl+O` → `Enter` → `Ctrl+X`) 후 **반드시 재생성**한다 — `restart`가 아니다.
`.env`는 컨테이너를 **만들 때**만 읽히고 `get_settings()`가 `lru_cache`라, `restart`로는
반영되지 않는다(배포_실행순서 §6-1과 동일한 주의).

```bash
docker compose up -d --force-recreate llm-api llm-worker
docker compose exec llm-api printenv BACKEND_BASE_URL       # 반영됐는지 눈으로 확인
docker compose exec llm-api printenv BACKEND_SERVICE_TOKEN  # 반영 확인 — 화면에 값이 뜨니 주변에 안 보이게 주의
```

### 2-4. 계약 검증 스크립트 실행

**반드시 최신 `origin/main`(PR #27 포함) 기준으로.** 배포 VM의 코드가 최신인지 먼저 확인:

```bash
git log --oneline -1
```

그 다음 실행:

```bash
docker compose exec llm-api python scripts/verify_backend_contract.py \
  --base-url <백엔드 주소> --token <BACKEND_SERVICE_TOKEN 값> \
  --team-id 1 --expense-id <백엔드에게 받은 지출 ID>
```

읽는 법:

- **CRITICAL 실패**(지출 상세·team_settings)면 **여기서 멈춘다** — 이 상태로는 심사가
  시작되지 않는다. camelCase 힌트가 뜨면 백엔드에 필드명 정정을 요청한다.
- **BE-007(멤버명단)·BE-009(지출이력) 관련 DEGRADED는 정상**이다 — 미구현이 이미
  확정된 항목이니 실패로 놀라지 않는다.
- 그 외 DEGRADED는 자동 처리율이 떨어진다는 신호일 뿐 배포를 막는 것은 아니다.

### 2-5. 신규 카테고리 4종 콜백 저장 확인

교통·장소_대관·비품·행사_활동 중 하나로 실제 지출을 심사시켜 콜백이 백엔드에 정상
저장되는지 확인한다.

- **저장이 실패해도 우리 결함이 아니다.** 백엔드 ENUM 마이그레이션이 AWS 배포와 함께
  적용될 예정이라 아직 안 끝났을 수 있다 — 실패하면 우리 쪽 결함으로 단정하지 말고
  백엔드에 마이그레이션 완료 여부부터 확인한다(기존 합의).

### 2-6. 실연동 E2E 1건

1. `POST /v1/analyze`로 실지출 1건 심사를 요청한다.
2. 워커 로그에서 `job … succeeded`를 확인한다.
3. 콜백이 2xx로 갔는지 확인한다(워커 로그 또는 `GET /v1/jobs/{job_id}`).
4. **백엔드 화면에서 그 지출의 상태가 실제로 바뀌었는지** 눈으로 확인한다 — 여기까지
   되면 실연동 완료다.
