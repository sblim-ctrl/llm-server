## 0. 새 작업 시작 — 브랜치·워크스페이스 만들기

### 브랜치 이름 규칙

`T1`~`T14` 같은 번호 체계는 2026-08-06 이후로 쓰지 않는다. 최근 브랜치는 전부 `타입/주제-kebab-case` 형식이다.

| 타입 | 쓰는 경우 | 예시 |
|---|---|---|
| `feat/` | 새 기능 | `feat/eval-category-scoring` |
| `fix/` | 버그 수정 | `fix/hitl-resume-requires-real-interrupt` |
| `docs/` | 문서만 | `docs/checklist-smoke-done` |
| `chore/` | 배포·운영·잡일성 작업 | `chore/backend-connect-live` |
| `ci/` | CI 설정 | `ci/timeout-covers-runner-wait` |
| `test/` | 테스트만 | `test/fewshot-catalog-contract` |

주제는 **영어 kebab-case**로, 무슨 작업인지 한눈에 보이게 짧게(3~6단어).

### Orca 워크스페이스 만들기

```bash
orca worktree create chore/backend-connect-live
```

⚠️ **주의 3가지** (겪었던 함정):

1. **슬래시가 하이픈으로 치환된다.** 워크스페이스 디렉터리는 `~/orca/workspaces/llm-server/chore-backend-connect-live`로 생기고, `autoRenameBranchFromWork` 설정 때문에 실제 git 브랜치도 하이픈 형태로 붙을 수 있다. 생성 직후 반드시 확인·정정:
   ```bash
   git branch --show-current
   git branch -m chore/backend-connect-live   # 하이픈으로 붙었으면 슬래시로 되돌림
   ```
   **push 전에 한 번 더 확인할 것** — 하이픈 브랜치가 원격에 올라가면 되돌리기 번거롭다.

2. **`.env`는 자동으로 안 따라온다.** gitignore 대상이라 워크스페이스마다 수동으로 복사해야 한다:
   ```bash
   cp ~/orca/workspaces/llm-server/<기존워크스페이스>/.env ~/orca/workspaces/llm-server/chore-backend-connect-live/.env
   ```

3. 작업 시작 전에 **원격과의 divergence를 확인**한다 (아래 §1-0 참고).

## Part 1. 로컬 — 코드 변경 → 커밋 → 푸시 → PR → 머지

### 1-0. 시작 전 divergence 확인

다른 사람이 먼저 main에 뭔가 올렸을 수 있다. 작업을 시작하기 전, 그리고 push 하기 직전 다시 한번 확인한다.

```bash
git fetch origin main
git rev-list --count --left-right origin/main...HEAD
# "0  N" → 정상 (로컬만 N개 앞섬)
# "N  0" → origin이 앞서 있다. git pull 먼저
# "N  M" → 갈라졌다. 무엇이 갈렸는지 보고 수동 정리
```

**로컬에 커밋 안 된 변경이 있는 채로 pull해야 하면** stash를 쓴다 — 실제로 겪은 패턴:

```bash
git stash push -u -m "작업중인 내용 설명"
git pull origin main          # 이제 fast-forward로 깔끔하게 됨
git stash pop
```

`stash pop`에서 충돌이 나면(양쪽이 같은 줄을 건드린 경우) 파일을 열어 `<<<<<<< Updated upstream` / `=======` / `>>>>>>> Stashed changes` 사이를 직접 읽고 — **어느 한쪽을 기계적으로 고르지 말고, 두 변경의 의도를 각각 파악해서** 합친다. 끝나면:

```bash
grep -rn '^<<<<<<<\|^=======$\|^>>>>>>>' --include='*.py' .   # 남은 충돌 마커 없는지 확인
git add <해결한 파일>
git stash drop   # 완전히 복구됐으면 정리
```

### 1-1. 무엇이 바뀌었는지 확인

```bash
git status --short
git diff --stat
```

### 1-2. 스테이징 — 파일을 **개별 지정**한다

```bash
git add app/foo.py app/bar.py tests/test_foo.py
```

**`git add -A`나 `git add .`는 쓰지 않는다.** 이 저장소엔 `.claude/`·`.codex/`·`.git_hooks/`·`AGENTS.md` 같은, 로컬 툴링이 만든 미추적 파일이 항상 섞여 있다 — 통째로 add하면 의도치 않게 커밋에 끼어든다.

```bash
git status --short   # 스테이징된 파일이 의도한 목록과 정확히 일치하는지 다시 확인
```

### 1-3. 커밋

Conventional commits, 한국어 본문. **`Co-Authored-By` 트레일러는 붙이지 않는다** (이 저장소 관례).

```bash
git commit -m "$(cat <<'EOF'
fix: 짧은 요약 한 줄

- 무엇을 왜 바꿨는지
- 영향 범위
EOF
)"
```

### 1-4. 푸시 + PR 생성

```bash
git push -u origin <브랜치명>

gh pr create --base main --title "제목" --body "$(cat <<'EOF'
## 요약
- ...

## 검증
- uv run pytest -q → ...
EOF
)"
```

### 1-5. CI 확인

```bash
gh pr checks <PR번호> --json name,state,bucket,link
```

`state`가 전부 `SUCCESS`고 `bucket`이 `pass`면 통과. 실패면 `link`로 들어가 로그 확인.

머지 가능 상태인지도 같이 본다:

```bash
gh pr view <PR번호> --json mergeable,mergeStateStatus,reviewDecision
```

`mergeStateStatus`가 `CLEAN`이어야 한다. `DIRTY`면 base와 충돌, `BLOCKED`면 리뷰 등 다른 게이트가 남은 것.

### 1-6. 머지

이 저장소는 **일반 머지 커밋**(`Merge pull request #N from ...`)을 쓴다 — squash도 rebase도 아니다.

```bash
gh pr merge <PR번호> --merge
gh pr view <PR번호> --json state,mergedAt,mergeCommit   # 머지됐는지 확인
```

## Part 2. VM — 배포 반영

VM이 이미 떠 있고, main에 새 커밋이 들어간 상태에서 그걸 실제 서비스에 반영하는 절차.

### 2-1. SSH 접속

GCP 콘솔 → Compute Engine → 인스턴스 줄의 `SSH` 버튼.

### 2-2. 잡 큐 확인 — **재배포 직전 필수**

재빌드 중 워커가 재시작되면 그 순간 처리 중이던 잡이 끊길 수 있다. `running` 잡이 있으면 끝날 때까지 기다린다.

```bash
cd ~/llm-server
docker compose exec llm-postgres psql -U budgetops -d budgetops_llm \
  -c "SELECT status, count(*) FROM jobs WHERE status IN ('queued','running') GROUP BY status;"
```

### 2-3. 롤백 대비 — 현재 커밋 기록

```bash
git log --oneline -1
```

### 2-4. 코드 받기

```bash
git pull
```

> **`Your local changes would be overwritten` 에러가 나면** — VM의 `docker-compose.yml`은 배포 당일 포트를 `127.0.0.1:5433:5432`로 직접 고쳐둔 로컬 수정이 있다 (`배포_실행순서_2026-08-07.md` §4-1). 그 부분과 충돌한 것이므로:
> ```bash
> git stash && git pull && git stash pop
> ```

### 2-5. 재빌드가 필요한지 판단

Dockerfile이 이미지에 복사하는 것은 다음뿐이다(2026-08-10 기준):

```
app/  prompts/  templates/  reference_docs/  eval/  scripts/  models.yaml  pyproject.toml  uv.lock
```

| 이번에 바뀐 것 | 재빌드 필요? |
|---|---|
| 위 목록 안의 파일(코드·프롬프트·템플릿·eval·models.yaml) | **필요** — 이미지에 안 들어가면 반영 안 됨 |
| `docs/`·`README.md` 등 문서만 | 불필요 |
| DB 스키마(`app/db/schema.sql`) | 재빌드는 필요하지만 마이그레이션 명령은 없음 — `apply_schema()`가 기동 시 멱등하게 적용 |
| `.env`만 | 재빌드 불필요, **재생성**만 필요 (§3 참고) |

재빌드가 필요하면:

```bash
docker compose up -d --build llm-api llm-worker
```

`llm-postgres`는 이미지 자체가 `pgvector/pgvector:pg16`(빌드 대상 아님)이라 스키마 변경이 없는 한 대상에서 뺀다.

### 2-6. 상태 확인

```bash
docker compose ps                              # 3개 컨테이너 전부 Up
curl localhost:8000/healthz
curl "localhost:8000/readyz?deep=true"         # 200이면 OpenAI 키까지 살아있다는 뜻
```

### 2-7. 이번 변경이 실제로 반영됐는지 눈으로 확인

예: API 응답 필드를 뺐다면 그 필드가 정말 없는지, 새 엔드포인트를 추가했다면 정말 뜨는지 `curl`로 직접 찍어본다. 자동화된 검증이 이미 있으면 그걸 돌린다:

```bash
docker compose exec llm-api python scripts/verify_backend_contract.py \
  --base-url <백엔드주소> --token <SERVICE_TOKEN> \
  --team-id <실재 팀ID> --expense-id <실재 지출ID>
```

## 3. `.env`만 바꿨을 때

⚠️ **`docker compose restart`로는 반영되지 않는다.** `.env`는 컨테이너를 **만들 때만** 읽히고, `get_settings()`는 `lru_cache`라 프로세스 안에서 다시 안 읽는다. 재시작이 아니라 재생성이 필요하다.

```bash
nano .env
docker compose up -d --force-recreate llm-api llm-worker

# 반영 확인
docker compose exec llm-api printenv BACKEND_BASE_URL
```

컨테이너는 멀쩡히 `Up`으로 보이는데 지출 조회·콜백만 전부 실패하는 게 이 실수의 전형적인 증상이다.

## 4. 배포 전 게이트 (코드가 바뀐 PR이면)

```bash
docker compose up -d llm-postgres
export OPENBLAS_NUM_THREADS=1

uv run pytest -q                            # 전체 통과
uv run python scripts/predeploy_check.py    # openapi 드리프트·카테고리 9종·서비스 토큰 기본값 등 자동 점검
uv run python -m eval.run_eval              # 골든셋 — 오승인 0건 하드 게이트, 정확도 ≥90%
```

**CI 빨간불은 진짜 결함 신호다** (2026-08-06 T9 머지로 예전의 "run_eval 전건 실패는 정상"이던 시기는 끝났다). 예전 기준으로 넘기지 말 것.

실키 비용이 드는 검증(실모드 스모크)은 분류 경로나 프롬프트를 바꿨을 때만:

```bash
MOCK_LLM=false uv run python scripts/smoke_real_mode.py   # 약 $0.10
```

라우트·스키마를 바꿨다면 `docs/openapi.json`을 재생성해서 같은 PR에 포함시킨다 (CI가 자동으로 잡아주지 않는다 — `predeploy_check.py`가 사람이 돌려야 잡는 항목):

```bash
uv run python scripts/dump_openapi.py
```

## 5. 문제 생겼을 때 — 롤백

```bash
cd ~/llm-server
git log --oneline -5              # §2-3에서 적어둔 이전 커밋 확인
git checkout <이전 커밋>
docker compose up -d --build llm-api llm-worker
```

- `.env`는 git 바깥이라 롤백해도 그대로 유지된다.
- DB는 이번 배포에서 스키마 파괴 변경이 없는 한(대부분 그렇다) 되돌릴 게 없다 — `apply_schema()`가 멱등이라 구버전 코드로 돌아가도 그대로 동작한다.
- 롤백 후에는 §2-2(잡 큐)·§2-6(상태 확인)을 다시 거친다.
