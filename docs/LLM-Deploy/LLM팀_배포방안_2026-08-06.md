# LLM 서버 배포 방안

작성 2026-08-06 · 개발자 A · **배포 목표 2026-08-07(금) 오후**

---

## 1. 결론

**GCE 인스턴스 1대에 현재 `docker-compose.yml`을 그대로 올립니다.** Cloud Run·Cloud SQL 같은 관리형 서비스는 이번 배포에서 쓰지 않습니다.

```
GCE 인스턴스 1대 (e2-medium · 서울 리전 · Ubuntu 22.04)
└─ Docker
   ├─ llm-api      uvicorn, 8000 포트   ← 백엔드가 호출
   ├─ llm-worker   상시 폴링 프로세스
   └─ llm-postgres pgvector/pgvector:pg16
```

현재 저장소의 `docker-compose.yml`이 이 3개를 이미 정의하고 있고, 로컬에서 검증된 구성 그대로입니다. **VM에서 실행하는 명령은 `docker compose up -d --build` 한 줄입니다.**

---

## 2. 왜 이 선택인가

관리형 서비스(Cloud Run + Cloud SQL)도 검토했고, **가능은 하지만 이번 일정에서는 손해**라고 판단했습니다.

| 쟁점 | 관리형(Cloud Run + Cloud SQL) | VM + compose |
|---|---|---|
| **pgvector** | Cloud SQL PG15+에서 지원되지만, 인스턴스 생성 → 확장 활성화 → 비공개 IP·VPC 커넥터 설정이 별도로 필요 | `pgvector/pgvector:pg16` 이미지에 포함 — 설정 0 |
| **상시 워커** | Cloud Run은 요청 기반이라 폴링 워커를 올리려면 `min-instances=1` + CPU 상시 할당(사실상 VM 비용) 또는 Cloud Run Jobs + 스케줄러로 재구성 | 컨테이너 하나. 구조 변경 없음 |
| **AWS 이전** | Cloud Run·Cloud SQL은 GCP 전용 → EC2 이전 시 재작성 | EC2에서 같은 `docker compose up -d`. **거의 그대로 이식** |
| **팀 학습량** | VPC 커넥터·Secret Manager·IAM·서비스 계정 등 새 개념 다수 | 새로 배울 것은 "인스턴스 1대 만들기"뿐 |
| **로컬과의 동일성** | 로컬(compose)과 운영(관리형)이 달라져 재현이 어려움 | **완전히 동일** — 로컬 문제 = 운영 문제 |

**결정 근거를 한 줄로**: 풀스택팀이 실배포를 AWS로 옮길 예정이므로, GCP 전용 서비스에 묶이지 않는 편이 낫습니다. 여기에 팀 배포 경험이 없고 D-1이라는 점이 더해져 **"로컬에서 검증된 것을 그대로 옮기는" 방식**이 위험이 가장 작습니다.

## 3. 실행 순서와 소요

절차서: `docs/LLM-Deploy/배포_실행순서_2026-08-07.md` (복붙 가능한 명령 전문)

| 단계 | 내용 | 소요 | 풀스택 답변 필요 |
|---|---|---|---|
| 1 | GCE 인스턴스 생성 (콘솔) | 5분 | — |
| 2 | SSH 접속 → Docker 설치 | 3분 | — |
| 3 | `git clone` | 1분 | — |
| 4 | `.env` 작성 (실키·토큰) | 5분 | — |
| 5 | `docker compose up -d --build` → `/readyz?deep=true` 200 확인 | 10분 | — |
| 6 | 백엔드 주소 연결 · 방화벽 | 5분 | **✅** |
| 7 | 실지출 1건 E2E · 회칙 파일 인덱싱 | 30분 | **✅** |

**1~5는 풀스택 회신과 무관하게 오늘 중 끝낼 수 있습니다.** 회신이 늦어도 배포 준비 자체는 막히지 않습니다.

> **6단계(프로젝트·VPC·방화벽 협의)가 길어질 것 같으면**: 로컬 스택 + 터널(`cloudflared tunnel --url http://localhost:8000`)로 **임시 HTTPS 주소를 먼저 넘길 수 있습니다.** 10~15분이면 되고 방화벽·IP 협의가 아예 필요 없어, 백엔드가 연동 테스트를 그 사이에 시작할 수 있습니다. 노트북을 켜 둬야 하고 실행할 때마다 주소가 바뀌므로 **VM 배포를 대체하지 않고 그 전까지만** 씁니다. 절차는 `docs/LLM-Deploy/배포_실행순서_2026-08-07.md` 부록에 있습니다.

### 사양 근거

**e2-medium(2 vCPU · 4GB)** — 컨테이너 3개 상시 구동 + 이미지 빌드 기준입니다. e2-small(2GB)은 부족할 위험이 있고, 상위 사양은 MVP 트래픽에 불필요합니다.

> **초안의 근거는 정정하되 사양 선택은 유지합니다.** "회칙 인덱싱 시 임베딩 연산이 메모리를 쓴다"고 적었으나, 임베딩은 OpenAI API 호출이라 이 서버에서 계산하지 않습니다(`app/llm/client.py:187` — `OpenAIEmbeddings`). 로컬 임베딩 모델·torch 의존성이 없어 메모리 급증 요인은 아닙니다. 다만 컨테이너 3개 + 빌드 기준으로는 4GB가 안전하므로 e2-medium은 그대로 갑니다.

### 마이그레이션

**별도 단계 없습니다.** API·워커가 기동 시 `apply_schema()`로 테이블·인덱스·pgvector 확장을 생성합니다(`app/main.py:44`, `app/worker.py:305`). 멱등이라 재기동해도 안전합니다.

## 4. 풀스택팀에 요청할 것

배포 자체는 독립적으로 되지만, **연동에는 아래가 필요합니다.** (1~3은 초안, 4~5는 검토에서 추가)

| # | 필요한 것 | 없으면 |
|---|---|---|
| 1 | **백엔드 주소** (내부 IP 또는 호스트명) | `BACKEND_BASE_URL` 기본값이 `localhost:8080`이라 지출 조회·콜백이 전부 실패 |
| 2 | **백엔드 IP** (방화벽 제한용) | 같은 VPC면 불필요(아래 참조), 다른 프로젝트면 포트를 열 범위를 특정할 수 없음 |
| 3 | **GCP 프로젝트·리전** (백엔드 dev 서버가 GCP인지부터) | 다른 리전이면 호출마다 지연이 붙음 |
| 4 | **우리를 백엔드 GCP 프로젝트에 초대해 줄 수 있는지** (IAM Compute 권한) | 초대되면 같은 VPC 내부 IP 통신(경우 A) — 방화벽 설정이 아예 없어 가장 빠르고 안전. 안 되면 경우 B |
| 5 | **테스트용 실데이터** — 실재하는 팀(모임) ID 1개 + 그 팀의 지출 ID 1개 | `verify_backend_contract.py` 실행에 필수. 없으면 배포 당일 검증 단계에서 대기 |

우리가 전달할 값: **서버 주소 · 포트 8000 · `SERVICE_TOKEN`**

> **방화벽 참고 — "같은 VPC"는 저절로 되지 않습니다.** 우리 계정에 새 프로젝트를 만들어 VM을 올리면 백엔드와 다른 프로젝트·다른 VPC이므로 **자동으로 경우 B**(외부 IP + 백엔드 IP를 소스로 하는 방화벽 규칙)입니다. **경우 A**가 되려면 위 4번 초대를 받아 **백엔드 프로젝트 안에서** 인스턴스를 만들어야 하고, 그때는 `default` 네트워크의 기본 규칙 `default-allow-internal`이 내부 통신을 허용하므로 추가 규칙이 필요 없습니다(백엔드가 `default`가 아닌 커스텀 VPC를 쓰면 이 규칙이 없을 수 있어 확인 필요). 어느 경우든 인스턴스 생성 시 HTTP/HTTPS 허용을 체크하지 않으므로 인터넷에서는 닫혀 있습니다.
>
> 백엔드가 GCP 밖(사내망·개인 PC)에 있으면 VPC 논의 자체가 성립하지 않고, 고정 IP가 없으면 경우 B의 방화벽 규칙도 쓰기 어렵습니다. 그때는 §3의 터널 방식이 사실상 유일한 단기 수단입니다.

## 6. 이번 배포에서 하지 않는 것 (의도적)

MVP 시연 범위로 한정했습니다. 실서비스 전에는 처리해야 합니다.

| 항목 | 현재 | 실서비스 전 |
|---|---|---|
| **DB 영속성** | 컨테이너 볼륨(VM 디스크). VM 삭제 시 데이터 소멸 | 관리형 DB(Cloud SQL / RDS)로 이전 + 자동 백업 |
| **HTTPS** | 평문 HTTP. 내부 통신 전제 | 로드밸런서 + 인증서 |
| **비밀 관리** | VM 위의 `.env` 파일 | Secret Manager |
| **다중화** | 인스턴스 1대. 재부팅 시 중단 | 인스턴스 그룹 · 워커 수평 확장(`replicas` 지점은 이미 있음) |
| **CI/CD** | `git pull` 후 수동 재배포 | 파이프라인 |
| **모니터링** | `docker compose logs` | Cloud Logging |

**AWS 이전 시**: EC2 인스턴스에서 동일한 `docker compose up -d`로 동작합니다. 바뀌는 것은 인스턴스 생성 절차와 방화벽(보안 그룹) 설정뿐이고, 애플리케이션 구성과 명령은 그대로입니다. DB를 RDS로 옮길 경우 `DATABASE_URL` 한 줄 교체 + RDS에서 pgvector 확장 활성화가 추가됩니다.

## 7. 배포 전 확인 사항

`docs/LLM-Deploy/T8_배포체크리스트_2026-08-07.md`에 전체가 있고, 배포 방식과 직결되는 것만 옮깁니다.

**배포 기준 코드는 `ce18f7e`입니다.** 이 문서 초안(8/6) 이후 PR #22(T9 골든셋)·#23(백엔드 회신 반영 — team_type 언더바 변환·기준 금액 0 허용)·#24(T11 문서 동기화)·#26(배포 이미지에 scripts 포함)이 더 머지됐습니다. **게이트 3종은 이 최종 main에서 다시 돌려 기준선을 새로 잡습니다.**

- **잡 큐 드레인** — #17이 심사 그래프 노드 순서를 바꿔서, 구 배선으로 기록된 체크포인트가 신 배선에서 재개되면 `intake_receipt`를 건너뛸 수 있습니다. 배포 직전 `queued`·`running` 잡이 0인지 확인하고 올립니다. (`PROGRESS.md:296`에도 기록)
- **이미지 재빌드 필수** — `prompts/classifier/v6.yaml`이 신설됐고, Dockerfile이 `prompts`를 이미지에 복사합니다. 재빌드 없이는 반영되지 않습니다.
- **`SERVICE_TOKEN` 교체 필수** — 기본값 `dev-service-token-change-me`가 남아 있으면 `/readyz`가 실모드에서 not_ready로 떨어집니다(설계된 가드).
- **실모드 스모크 1회** — T7 머지로 분류 경로가 바뀌었으므로(OCR 선행·프롬프트 v6) 배포 전 `smoke_real_mode.py`를 한 번 돌립니다. 약 $0.10.
- **`.env` 수정은 재기동이 아니라 재생성으로 반영됩니다** — `env_file`은 컨테이너를 **만들 때** 읽히고 `get_settings()`가 `lru_cache`라, `docker compose restart`로는 반영되지 않습니다. `BACKEND_BASE_URL`을 나중에 채우는 절차(실행순서 §6-1)에서 특히 위험합니다 — 컨테이너는 `Up`인데 조회·콜백만 전부 실패합니다. `docker compose up -d --force-recreate llm-api llm-worker`를 씁니다.
- **`scripts/`는 이미지에 포함됩니다 (초안 시점에서 정정)** — PR #26 머지(main `ce18f7e`)로 Dockerfile에 `COPY scripts ./scripts`가 추가됐습니다(`Dockerfile:18`). 배포 직후 `verify_backend_contract.py`를 `docker compose exec llm-api python scripts/verify_backend_contract.py …`로 그대로 돌릴 수 있어, 별도의 볼륨 마운트가 필요 없습니다(`docs/LLM-Deploy/배포_실행순서_2026-08-07.md` §6-4).
- **Postgres 5433 포트가 호스트에 열립니다** — `docker-compose.yml`의 로컬 개발용 설정입니다. VM에서는 같은 VPC의 다른 서버가 `budgetops/budgetops`로 DB에 직접 붙을 수 있으므로 `127.0.0.1:5433:5432`로 바꿔 둡니다(실행순서 §4-1). 컨테이너 간 통신은 포트 매핑과 무관해 영향이 없습니다.
