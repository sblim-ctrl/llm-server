이 파일이 곧 현재 계약입니다.

## 팀별 AI 에이전트 모델

팀마다 별도 LLM API·워커 프로세스 또는 컨테이너를 생성하지 않습니다. 프로세스는 모든 팀이
공유하고, 심사할 때 `teamId`를 기준으로 팀별 설정·예산·회칙·판례를 로드합니다. 회칙과 판례
인덱스도 `teamId`와 버전으로 격리합니다.

따라서 모임 생성 시 말하는 “에이전트 생성”은 프로세스 기동이 아니라 아래 데이터 준비를 뜻합니다.

```text
API-009 기본 모임·관리자·예산·설정 생성
  → API-029 설정 확정
  → API-031 기본/사용자 정책 저장
  → /v1/context/refresh 비동기 인덱싱
  → policySyncStatus=READY
```

외부 LLM 호출은 API-009 또는 API-031의 DB 트랜잭션 안에서 실행하지 않고, DB 커밋 후 Outbox
워커가 호출하는 방식을 제안합니다. 인덱싱 준비 전이나 실패 시에는 `autoApprove=false`로
해석해 자동 승인으로 이어지지 않게 합니다.

API-009·029·031·044 필드와 상태값의 전체 제안은
[`풀스택_팀별_AI에이전트_연동제안.md`](풀스택_팀별_AI에이전트_연동제안.md)를 참조해 주세요.

## 1. 인증

**모든 엔드포인트**에 서비스 토큰이 필요합니다.

```
Authorization: Bearer <SERVICE_TOKEN>
```

토큰이 없거나 틀리면 `401 {"detail": "invalid service token"}`입니다.

면제 경로 (토큰 없이 접근 가능):

| 경로 | 용도 |
|---|---|
| `/healthz` | 라이브니스 |
| `/readyz` | 레디니스 (DB·의존성 점검) |
| `/docs`, `/redoc`, `/openapi.json` | API 문서 — 서버가 떠 있으면 브라우저로 바로 확인 가능 |
| `/ui` | 데모 대시보드 페이지 껍데기 (내부 fetch는 토큰을 실어 보냄) |

> 근거: `app/middleware/auth.py` `PUBLIC_PATHS`

위 4줄이 면제의 전부입니다. 표에 없지만 `/mcp`가 마운트되어 있는데(MCP 읽기 툴 4종 —
저희 내부 디버깅·시연용이라 연동 대상은 아닙니다), **이 경로도 서비스 토큰이 필요합니다.**
앞단에 게이트웨이를 두신다면 공개 경로로 분류하지 말아 주세요.

반대 방향(저희가 백엔드 내부 조회 API를 호출할 때)은 별도 토큰 `BACKEND_SERVICE_TOKEN`을
씁니다 — 위 `SERVICE_TOKEN`과는 다른 값입니다. 이 방향의 상세는
[`백엔드_요구_내부API_명세.md`](백엔드_요구_내부API_명세.md)를 참조해 주세요. 이 값도
저희가 생성해서 보안 채널로 전달합니다.

## 2. 심사 흐름 — 비동기입니다

가장 중요한 계약입니다. `POST /v1/analyze`는 **결과를 그 자리에서 돌려주지 않습니다.**

```
[백엔드]  POST /v1/analyze          ──►  [LLM 서버]   접수만 하고 202 즉시 응답
                                                        (LLM 호출 없음, 워커가 뒤에서 처리)

[백엔드]  POST /agent-callback      ◄──  [LLM 서버]   심사 완료 시 결과 발신
                                                        ★ 이 수신 엔드포인트를 만들어 주셔야 합니다

[백엔드]  GET /v1/jobs/{job_id}     ──►  [LLM 서버]   폴링 fallback (콜백 유실 대비)
```

### 2-1. `POST /v1/analyze` — 심사 요청

요청 본문 (5필드, camelCase):

```json
{
  "jobId": "be-job-20260729-001",
  "expenseId": 4821,
  "organizationId": 17,
  "reviewGoal": "회칙·예산·판례에 근거해 이 지출의 승인 여부를 심사하라",
  "receiptPath": "https://.../receipts/exp-4821.png"
}
```

- 필수: `jobId`, `expenseId`, `organizationId`
- `expenseId`와 `organizationId`는 백엔드 DB의 `BIGINT`에 맞춘 JSON `integer(int64)`
- **`jobId`는 JSON `string`입니다** — `expenses.ai_job_id`가 `VARCHAR(36)`(UUID)이라
  들으신 대로 문자열로 두었습니다. 저희는 검증 없이 그대로 echo만 합니다
- `reviewGoal` 기본값 `""`, `receiptPath`는 nullable

> ⚠️ **ID 타입이 필드마다 반대 방향으로 엄격합니다.** 세 필드가 한 요청 안에 같이 오는데
> `jobId`는 문자열만, 나머지 둘은 정수만 받습니다. 어긋나면 `422`입니다.
>
> | 보내는 값 | 결과 |
> |---|---|
> | `"jobId": "be-job-001"` · `"jobId": "12345"` | ✅ |
> | `"jobId": 12345` | ❌ `422` (`string_type`) |
> | `"expenseId": 4821` | ✅ |
> | `"expenseId": "4821"` | ❌ `422` (`int_type`) |
>
> "BIGINT로 통일했다니 `jobId`도 숫자겠지"라고 보내시면 첫 호출부터 422가 납니다.
>
> ✅ **2026-08-04 회신으로 문자열 확정** — 저희 타입은 이대로 둡니다. 이 항목은 종결입니다.
- **지출 상세(제목·금액·날짜 등)는 보내지 않으셔도 됩니다** — 저희가 내부 조회 API로
  되묻는 pull 모델로 구현돼 있습니다 (§5의 미확정 항목 참조)

응답 `202`:

```json
{ "job_id": "9f2c...", "external_job_id": "be-job-20260729-001", "status": "queued" }
```

- `job_id` = 저희 내부 잡 ID. `external_job_id` = 보내주신 `jobId` 그대로 echo.
- **같은 `expenseId`로 활성 잡이 이미 있으면 새로 만들지 않고 기존 잡을 재사용합니다**(멱등).
  이때 `job_id`가 기존 잡 ID로 돌아오므로, 중복 제출 여부를 이 값으로 판별하실 수 있습니다.

### 2-2. `GET /v1/jobs/{job_id}` — 폴링 fallback

`job_id`와 `external_job_id` **어느 쪽으로도 조회 가능**합니다.

```json
{
  "job_id": "9f2c...",
  "status": "succeeded",
  "attempts": 1,
  "result": { },
  "created_at": "2026-07-29T10:00:00+09:00",
  "updated_at": "2026-07-29T10:00:08+09:00"
}
```

`status` ∈ `queued` | `running` | `succeeded` | `failed` | `dead`
(`dead` = 재시도 소진). 없는 잡은 `404`.

## 3. 아웃바운드 콜백 — 만들어 주셔야 하는 엔드포인트

심사가 끝나면 저희가 이쪽으로 보냅니다.

```
POST {BACKEND_BASE_URL}/agent-callback
Content-Type: application/json
```

### 3-1. 페이로드 실제 예시

아래는 코드에서 실제로 직렬화한 결과입니다(`CallbackPayload.model_dump(mode="json", by_alias=True)`).

```json
{
  "jobId": "job-001",
  "expenseId": 4821,
  "teamId": 17,
  "verdict": "approve",
  "suggestedCategory": "도서",
  "processedBy": "AI",
  "confidence": 0.93,
  "opinions": [
    {
      "auditor": "evidence",
      "verdict": "pass",
      "summary": "영수증이 청구 내용과 일치합니다 (금액 32,000원) — 교보문고.",
      "evidence": ["영수증에서 읽은 값: 상호 교보문고 · 금액 32,000원 · 날짜 2026-07-07"],
      "figures": { "claimed_amount": 32000, "receipt_amount": 32000 },
      "similar_cases": []
    },
    {
      "auditor": "rule",
      "verdict": "pass",
      "summary": "회칙 부합",
      "evidence": ["제4조 도서 구입 인정"],
      "figures": { "amount": 32000 },
      "similar_cases": ["2026-06 유사 승인 1건"]
    }
  ],
  "mismatch": [
    { "field": "amount", "claimed": "32000", "receipt": "32000" }
  ],
  "reasons": {
    "requester": "승인되었습니다.",
    "admin": "잔액 182,000원 중 32,000원 집행."
  },
  "dryRun": false
}
```

> **최상위 키는 11개입니다.** 이전 버전에는 `modelVersion`·`promptVersion`·`costUsd`·
> `latencyMs` 4개가 더 있었으나 지출 상세 화면 어디에서도 쓰이지 않아 콜백에서 뺐습니다.
> 값 자체는 저희 쪽에 그대로 남아 `GET /v1/jobs/{job_id}`의 `result`로 조회됩니다.
> **전환 중에는 이 4개가 더 실려 올 수 있으니, 모르는 필드는 무시하도록 파서를 만들어
> 주세요.** 위 11개는 두 버전 모두에서 항상 옵니다.

### 3-2. 필드

| 필드 | 타입 | 필수 | 설명 |
|---|---|:--:|---|
| `jobId` | string | ✅ | 보내주신 `jobId` 그대로 |
| `expenseId` | integer(int64) | ✅ | 백엔드 `expenses.id`와 동일한 지출 ID |
| `teamId` | integer(int64) | ✅ | 요청의 `organizationId`와 동일한 값 |
| `verdict` | `approve`\|`reject`\|`escalate` | ✅ | 최종 판정 → API-046 `finalVerdict` |
| `suggestedCategory` | string\|null | | AI 카테고리 분류 결과 → API-046 `suggestedCategory`. **전역 9종 · 밑줄 표기** — 아래 참조 |
| `processedBy` | `"AI"`\|`"ADMIN"`\|null | | 최종 처리 주체 → API-046 `processedBy`. **에스컬레이션은 `null`** — 아래 3-2-1 참조 |
| `confidence` | float\|null | | 판정 신뢰도 |
| `opinions` | Opinion[] | | 심사관 4종 소견(회칙·예산·판례·증빙) → API-046 `detail`의 근거 재료 |
| `mismatch` | Mismatch[] | | 영수증-청구 불일치 항목 |
| `reasons` | `{requester, admin}` | | 사유 2종 → API-046 `detail`의 근거 재료 |
| `dryRun` | bool | | 기본 `false` |

> **2026-08-03 변경 — 관측 4필드를 뺐습니다.** `modelVersion` · `promptVersion` ·
> `costUsd` · `latencyMs`는 Figma 화면 설계 24장 어디에도 표시되지 않아 제거했습니다.
> 저희 성능·비용 계측용이었고, 이제 저희 잡 기록에만 남깁니다
> (`GET /v1/jobs/{job_id}`의 `result`로 조회 가능).
> **저장해서 쓰고 계셨다면 알려주세요 — 되돌리겠습니다** (회신요청 16번 ①).

**`Opinion`** — `auditor` ∈ `rule`\|`budget`\|`precedent`\|`evidence`, `verdict` ∈ `pass`\|`warn`\|`fail`\|`error`,
`summary`(필수) + `evidence`[] · `figures`{} · `similar_cases`[]

> **2026-08-11 갱신 — 증빙 심사관(`auditor: "evidence"`)이 네 번째 소견으로 실립니다**
> (2026-08-04 협의 8번, 지출 상세 'AI 심사결과'의 4번째 카드). 그동안 이 문서에 3종만
> 적혀 있던 것을 바로잡습니다.
>
> **배열 순서는 계약이 아닙니다.** 저희 내부 처리 순서(영수증 대조 → 회칙·예산·판례
> 병렬 심사) 그대로 나가 현재는 `evidence → budget → precedent → rule`이고, 저희
> 쪽에서 순서를 보장한 적이 없습니다 — **카드 매핑은 배열 위치가 아니라 각 항목의
> `auditor` 값으로 해주세요.** 영수증-청구 불일치로 심사관 3종을 건너뛰고 보류되는
> 건은 `opinions`에 `evidence` 하나만 실리는 등 **일부 심사관이 빠질 수 있어**, 위치
> 매핑은 순서를 어떻게 고정해도 이런 건에서 반드시 어긋납니다. (실사례: 데모 지출
> 상세에서 회칙↔증빙 카드 내용이 뒤바뀌어 표시 — 위치 매핑이 원인)
>
> 카드 표시 순서 자체도, 저희 내부 순서와 같은 **[증빙, 예산, 판례, 회칙]**으로
> 맞추실 것을 제안드립니다 — 증빙(영수증 대조)이 가장 먼저 나오는 값이라 화면과
> 코드 양쪽에서 "왜 이 순서인가"를 설명하기 쉽습니다. 다른 순서를 원하시면 저희가
> 맞추는 것도 가능하니 편하신 쪽으로 말씀해 주세요.

**`Mismatch`** — `field` ∈ `amount`\|`date`\|`merchant`\|`items`, `claimed`, `receipt` (전부 필수)

**`Reasons`** — `requester`(요청자용, 수치 없음) · `admin`(관리자용, 근거 수치 포함) 둘 다 필수

> **2026-08-05 확정 — `suggestedCategory`는 전역 9종을 밑줄 표기로 보냅니다.**
> `식비` · `교통` · `IT_인프라` · `교육` · `회의` · `장소_대관` · `행사_활동` · `비품` · `기타`
> ENUM에 슬래시를 넣을 수 없어 `IT_인프라` · `장소_대관` · `행사_활동`은 밑줄로 적습니다 —
> **화면의 슬래시 표기는 프론트가 출력할 때 만들어 주세요.** 서버·프롬프트·콜백은 밑줄 값
> 하나만 씁니다. 목록 원본은 `GET /v1/categories`이고 응답에 `version`이 있어 변경을
> 감지하실 수 있습니다(현재 `2`) — 값을 하드코딩하지 마시고 이 API를 쓰시길 권합니다.
> (종전 30종 매핑표 초안은 폐기됐습니다. 백엔드가 ENUM을 9종으로 확장해 주시면서
> 양쪽 목록이 같아졌습니다 — 그래서 매핑 자체가 필요 없어졌습니다.)

> 필드 대조 근거는 `app/schemas/callback.py` docstring에 있습니다 —
> API-046 `GET /api/expenses/{expenseId}/review-result` 응답
> `review{finalVerdict, detail, suggestedCategory, processedBy, createdAt}` 기준입니다.

#### 3-2-1. 'AI 자동처리' 배지 조건

`processedBy`는 **"최종 처리를 누가 했는가"**입니다. 판정이 무엇인가(`verdict`)와는 다릅니다.

| 상황 | `verdict` | `processedBy` | 배지 |
|---|---|---|---|
| AI가 승인까지 끝냄 | `approve` | `"AI"` | **AI 배지** |
| AI가 반려까지 끝냄 | `reject` | `"AI"` | **AI 배지** |
| AI가 관리자에게 올림(확인 대기) | `escalate` | `null` | 없음 |
| 관리자가 승인·반려함 | `approve`\|`reject` | `"ADMIN"` | 없음 |

즉 프론트 조건은 **`processedBy === "AI"` 한 줄**로 끝납니다.

에스컬레이션에 `"AI"`가 아니라 `null`을 보내는 것이 핵심입니다. 여기서 `"AI"`를 보내면
아직 관리자 확인을 기다리는 건이 화면에 "AI가 처리함"으로 표시됩니다. 키를 빼지 않고
**항상 명시적 `null`로** 실어 보냅니다 — 키 부재와 null을 구분하지 않으셔도 됩니다.

**확인 부탁드릴 것 두 가지입니다.**

1. **재심사 콜백이 `ADMIN`을 덮지 않게 해 주세요.** 같은 지출이 다시 심사되면 그 실행에는
   관리자 결정 정보가 없어 저희가 `processedBy: "AI"`로 보냅니다. 이미 관리자가 확정한
   건이면 저희 값으로 덮어쓰지 말아 주세요 — `processed_by`는 백엔드 소유 필드로
   정리돼 있습니다(DB 명세 "직접 UPDATE 금지"). 저희 쪽에서 막을 방법이 없는 지점입니다.
2. **지출 처리 이력(API-022)의 배지는 `processedBy`가 아니라 `actorType`으로 이해하고
   있습니다.** 맞다면 두 가지가 필요합니다 — ① `actorType`의 허용값, ② 저희 콜백이
   도착했을 때 `audit_logs`에 기록될 `event_type`. ②는 지금 ENUM에 "AI 심사 완료"에
   해당하는 값이 없어 미확정입니다(`풀스택_회신요청.md` 13번 ①). 이게 정해져야 AI가
   처리한 건이 이력에 남고 거기에 배지를 달 수 있습니다.

### 3-3. 재시도

- **최대 3회**, 지수 백오프 `1s → 2s` (3회째 실패 시 포기)
- 타임아웃 10초
- 3회 모두 실패해도 심사 잡은 죽지 않습니다 — 폴링 fallback(§2-2)이 최종 안전망입니다
- **따라서 같은 콜백이 중복 도착할 수 있습니다.** 멱등 처리 책임 소재는 미확정 항목입니다(§5)

## 4. 회신 부탁드리는 표기 불일치 2건

저희 코드에 실제로 있는 불일치입니다. **임의로 고치면 계약이 또 어긋나므로 현상 그대로 전달드립니다** —
어느 쪽으로 맞출지 정해 주시면 저희가 반영하겠습니다.

**① `/v1/analyze`의 요청과 응답 표기가 다릅니다**

| | 표기 |
|---|---|
| 요청 `AnalyzeRequest` | camelCase — `jobId`, `expenseId`, `organizationId`, `reviewGoal`, `receiptPath` |
| 응답 `AnalyzeAccepted` | **snake_case** — `job_id`, `external_job_id`, `status` |

`GET /v1/jobs/{job_id}` 응답도 snake_case(`job_id`, `created_at`, `updated_at`)입니다.

**② 콜백 `opinions[]` 안에서만 snake_case가 섞입니다**

콜백 최상위는 전부 camelCase인데, `opinions[].similar_cases` 하나만 snake_case로 나갑니다
(`evidence`·`figures`처럼 원래 한 단어인 필드는 차이가 드러나지 않습니다).
`Opinion`이 camelCase 별칭 설정을 상속받지 않는 구조라 생긴 차이입니다.

→ **전부 camelCase로 통일**이 자연스러워 보이는데, 풀스택 팀 파서에 이미 반영하신 게 있으면
알려주세요. 저희 쪽은 한 파일만 고치면 됩니다.
