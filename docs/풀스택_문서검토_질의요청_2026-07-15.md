| 항목 | 내용 |
|---|---|
| 작성일 | 2026-07-15 |
| 작성 | LLM 에이전트 개발팀 |
| 검토 대상 | `bravo_API명세서.xlsx`(API-001~048, 7/14 수신) · `bravo_기술아키텍처설계서.docx`(7/14 수신) |

| 목적 | 계약 동결 회의 안건. 각 항목에 양쪽 문서 원문 출처를 병기했으므로 회의에서 즉시 대조 가능 |

> **요약**: 심사 코어 인터페이스(payload·영수증 접근·실행 방식·상태 모델·타임아웃)가 서로 다른 전제로
> 작성되어 있다. 다만 "실행·트랜잭션은 백엔드 소유, 판례·임베딩은 LLM 소유"라는 경계 원칙은 양팀 문서가
> 일치하므로, 대부분 방향 충돌이 아니라 **인터페이스 확정** 문제다. **풀스택 액션이 실제로 필요한 코어는
> 아래 C2~C6 + Q2·Q3**이며, 특히 **Q2(ESCALATED 소견 저장처)·Q3(관리자 결정 전달 경로)**가 가장 급하다.
> 1회 회의로 동결 가능하다고 판단.
>
> **[정정] jobId 발급 주체 — 협의 불요.** 검토 초안에서 "통합 차단급"으로 분류했으나, 풀스택 payload 표에
> jobId가 **이미 첫 필드로 포함**되어 있어(백엔드 발급→콜백 대조) 풀스택 흐름은 자기완결적이다. 저희(LLM)가
> 들어온 jobId를 잡 키로 받아쓰면 되는 **LLM 내부 조정**이며 풀스택 액션은 없다. 아래 참고 항목으로만 남긴다.

## 1. 통합 전 확정 필요 인터페이스 — 회의에서 택일·동결 (C2~C6)

### (참고) jobId — 풀스택 액션 없음

풀스택 payload 표(docx 3-6 "심사 요청 payload", p.23)에 **`jobId`가 첫 필드**로 있고
"AgentInternalController 콜백 시 이 값으로 매칭"으로 규정돼 있다. 저희 설계서는 LLM이 job_id를 자체 발급해
202로 돌려주는 구조였는데, **저희가 백엔드 발급 jobId를 `AnalyzeRequest`에 수신해 잡 키로 채택**하도록
내부 조정하면 정합된다. 콜백·`GET /v1/jobs/{jobId}` 키도 동일 값으로 통일. **협의가 아니라 통보 사항.**

### C2. 승인/반려 실행 인터페이스

| | 내용 | 출처 |
|---|---|---|
| LLM 설계서 | 워커가 `POST {BE}/internal/agent/expenses/{id}/approve\|reject`(Idempotency-Key 헤더) 직접 호출 후 별도 콜백 | §4.1 execute_decision, §5.1, §7.1~7.2 |
| 풀스택 문서 | "Agent Server는 실행 권한이 전혀 없는 자문 역할" — 추천을 실은 **단일 콜백**(AgentInternalController)을 백엔드가 받아 확정·실행. 멱등성은 `expenses.version` 낙관적 락 + jobId 대조 | docx 5-1, 3-6 콜백, 6-4·6-6 |

**참고**: DB 트랜잭션(예산 차감)을 백엔드가 소유한다는 원칙은 LLM 설계서 §2.3도 동일하다.
충돌은 원칙이 아니라 **인터페이스 형태(명령 엔드포인트 2종+콜백 vs verdict 실은 콜백 단일)**뿐.

**LLM팀 제안**: 콜백 단일화(풀스택안) 수용 가능. 단, 콜백 응답으로 최종 반영 결과(전이된 status)를
돌려받아야 잡 종결 처리·판례 저장이 가능하다. 콜백 재시도 시 중복 반영 방지(콜백 멱등성)는
jobId 대조로 백엔드가 보장하는 것으로 이해 — 맞는지 확인 요청.

### C3. 심사 요청 payload 필드

| | 내용 | 출처 |
|---|---|---|
| LLM 설계서 | `expense_id, team_id, 제목·금액·카테고리(선택)·날짜·설명, receipt_signed_url, dry_run` | §7.2 |
| 풀스택 문서 | `jobId, expenseId, organizationId, 심사 목표, Spring 내부 영수증 조회 경로` + 콜백 주소 동적 전달. **지출 신청 내용(claim) 미포함 — Agent가 백엔드 재조회** | docx 3-6 '심사 요청 payload' 표, 백엔드 파이프라인 2 |

**확정할 것**: ① claim 포함 여부(미포함 확정 시 지출 상세 조회용 내부 API 신설 필요 — R1에 포함)
② '심사 목표' 필드의 실제 용도(자유 텍스트 지시라면 프롬프트 인젝션 경로가 되므로 enum 권장)
③ `team_id` vs `organizationId` 명칭 통일 ④ `dry_run`(P2) 필드 자리 예약 ⑤ callback_url 동적 전달 여부.

### C4. 영수증 접근 방식

| | 내용 | 출처 |
|---|---|---|
| LLM 설계서 | GCS Signed URL을 payload로 받아 직접 fetch (`parse_receipt(signed_url)`, REQ-025) | §2.1, §5.1 |
| 풀스택 문서 | "Agent Server가 직접 파일 저장소에 접근하지 않고, 반드시 Spring Boot를 한 번 더 거쳐 이미지를 받습니다(Agent 전용 토큰 인증)" | docx 1장 파일 스토리지, 3-6 payload 표, 대용량 파일 관리 |

**LLM팀 입장**: 백엔드 프록시안 수용 가능(Vision OCR이 아직 미구현이라 지금이 변경 적기).
단 프록시 응답 형식(바이너리 스트림? Signed URL 재발급?)과 이미지 조회 경로의 인증 방식을 명세로 확정 요청.

### C5. 지출 상태 모델 — 2026-07-06 합의와 다름

| | 내용 | 출처 |
|---|---|---|
| LLM 설계서 | `status(PENDING/APPROVED/REJECTED) × actor_type(AGENT/HUMAN)` 2축 — **7/6 양팀 공동 확정으로 기록(ADR-6)** | §7.3, ADR-6 |
| 풀스택 문서 | `expenses.status` 단일 enum `SUBMITTED/ESCALATED/APPROVED/REJECTED` + `expenses_reviews.processed_by(AI/HUMAN)` | docx 3-6 💡, 6-1 |

**확인 질문**: 7/6 합의가 폐기된 것인가, 문서가 합의 이전 버전인가?
기능적으로는 매핑 가능하므로(아래 표) 어느 쪽이든 **매핑표를 계약으로 동결**하면 된다:

| 2축 (설계서) | 풀스택 표현 |
|---|---|
| PENDING · AGENT | SUBMITTED |
| PENDING · HUMAN | ESCALATED |
| APPROVED/REJECTED · AGENT | status + processed_by=AI |
| APPROVED/REJECTED · HUMAN | status + processed_by=HUMAN |

콜백 `verdict` 값(approve/reject/escalate, 소문자)과 위 상태의 변환 책임은 백엔드(콜백 수신부)로 이해 — 확인 요청.

### C6. 콜백 타임아웃·레이스

| | 내용 | 출처 |
|---|---|---|
| LLM 설계서 | 노드별 30s 타임아웃 + 재시도 3회(지수 백오프), 콜백 3회 재시도, 백엔드 폴링 fallback 120s | §4.3, §8 |
| 풀스택 문서 | `ai_dispatched_at` 기준 **30초** 무콜백 → 폴링 1회 → ESCALATED 강제 전환(actor_type=SYSTEM) | docx 5-2 스케줄러, 백엔드 파이프라인 4 |

**문제**: p95 목표는 15s지만 OpenAI 재시도 1회만 발생해도 30s를 넘는다. 30s 강제 전환이면
정상 처리 가능한 건이 대량 ESCALATED되고, **뒤늦게 도착한 콜백과 스케줄러 전환이 경합**한다.

**LLM팀 제안**: ① 타임아웃 90~120s로 상향 협의 ② 늦은 콜백 규칙 동결 — 제안: 스케줄러가 이미
ESCALATED로 전환한 건의 콜백은 "상태 전이 없이 소견만 저장"(관리자 판단 참고용). ③ ESCALATED
전환 시 백엔드가 LLM `GET /v1/jobs/{job_id}`로 최종 확인하는지 여부(Q5와 연결).

## 2. 질문 (Q1~Q12)

**Q1. API-016 — 등록 시점 status 자동 결정.** 비고에 "팀 설정의 autoApprove, autoApproveLimit 값에
따라 등록 시점의 status가 SUBMITTED/ESCALATED/**APPROVED** 중 하나로 자동 결정"이라 되어 있다.
등록 시점에 AI 심사 없이 백엔드가 자동승인한다는 뜻인가? docx 본문(항상 SUBMITTED 저장 → AI 심사
→ 콜백으로 전이)과 모순되며, 사실이라면 REQ-012 fail-safe(어떤 실패도 자동 승인 금지)에 위배 +
AI 심사가 무력화된다. **문구 오류로 추정 — 확인 요청.**

**Q2. ESCALATED 건의 AI 소견 저장 위치. (최우선)** docx는 "애매하면 expenses.status만 ESCALATED로
바뀔 뿐 expenses_reviews는 아직 비어있습니다"(3-6, 6-1)라고 하는데, 같은 문서 화면 설명은
"ESCALATED 상태 건에는 AI 의견·위험도·회칙 근거를 함께 보여주고"(3-6 프론트 5)라고 한다.
REQ-014(심사관별 소견 표시)·REQ-026(보류 사유 포함 알림)·API-045(심사 결과 조회)도 소견 데이터가
필요하고, 7/6 협의 때의 `expenses.agent_result` 스냅샷(설계서 §2.3)은 현재 스키마에 없다.
**에스컬레이션 콜백 페이로드(opinions·reasons·mismatch)를 어디에 저장·노출할 계획인가?**
제안: expenses_reviews에 ESCALATED도 기록(final_verdict에 ESCALATED 추가 또는 별도 컬럼) 또는
expenses.agent_result JSON 컬럼 부활. — 에스컬레이션 건에서 관리자가 AI 소견을 보고 결정하는 것이
이 서비스 차별화의 핵심이라, 이 공백은 기능 자체를 막는다.

> **답변(7/16 슬랙) — 해결.** 백엔드가 `audit_logs` 테이블(신설 예정, DB 설계서 미전달분)에 감사 기록으로
> 저장. 콜백 payload(opinions·reasons·mismatch)의 저장처를 audit_logs로 확정 — 수용. R5 알림 조립 조인
> 대상도 동일 테이블로 정리됨.

**Q3. 관리자 결정 → LLM 전달 경로 (판례 학습 루프 입력).** docx 5-4는 "풀스택에서 할 일은 결정
기록(expenses_reviews)을 남겨두는 것뿐"이라 하는데, 그 결정이 LLM 서버로 전달되는 경로(설계서 §7.2
`POST /internal/agent/decisions` push 또는 LLM `/v1/precedents`로 push)가 어디에도 없다. 또한
override('AI와 다른 결정', ADR-9 `is_override`)와 그 사유를 기록할 필드도 스키마에 없다(REQ-015는
override 시 사유 필수). **push/pull 어느 방향으로 할지, override 필드를 추가할지 확정 요청.**
판례 루프는 "시간이 지날수록 똑똑해지는" 데모 핵심 그래프라 누락 시 REQ-042 미충족.

> **답변(7/16 슬랙) — pull 방향 합의 진행 중.** 풀스택은 pull(LLM이 직접 조회) 선호. LLM팀 동의 —
> 커서 기반 폴링(`GET {BE}/internal/agent/decisions?after_id=&limit=`, 60초 주기, 결정 id 기준 멱등
> upsert)으로 회신. 확정 대기: 조회 API 응답 필드(is_override·override_reason 포함), 레코드 원천
> (audit_logs 겸용 여부), 폴링 주기·인증(Agent 토큰 재사용).

**Q4. 승인 파라미터 매핑.** ① `escalation_threshold` = 설계서의 `force_escalation_amount`(무조건
에스컬레이션 금액, REQ-040상 금액)로 이해하면 되나? ② `auto_approve`(기본 FALSE) 마스터 스위치가
OFF일 때: 심사 자체를 생략하고 바로 ESCALATED인가, 심사는 수행하되 실행만 막나? (docx 3-6은 "auto_approve가
꺼져있으면 바로 에스컬레이션 추천"이라 하는데, 그 경우에도 관리자 참고용 소견은 생성하는 게 REQ-014에
부합 — LLM팀은 '심사는 수행, 자동 실행만 차단'을 권장) ③ API-009 응답 settings에는 `escalationThreshold`가
있는데 API-028(조회)/API-029(수정)에는 없다 — 명세 보완 필요. ④ confidence 임계치 θ(기본 0.8)는 LLM
내부 파라미터로 유지(백엔드 노출 불필요)로 이해 — 확인.

**Q5. 폴링 fallback 대상.** 백엔드 스케줄러/폴링이 LLM `GET /v1/jobs/{job_id}`를 호출하는 것인가?

드롭으로 봐도 되나? (LLM팀은 무관하나 요구사항 추적을 위해 확인)

**Q12. 문서 정리(사소).** ① docx의 API 번호가 명세서와 어긋남: docx API-041/042(ai-review/review-result,
명세서로는 API-044/045), API-046(reissue, 명세서 API-004), API-049(ai-summary, 명세서 API-024),
API-050(명세서에 없음) — v2 번호 체계로 재발행 요청. ② 마법사 서술 모순: "완료 클릭 시 API-009 한 번으로
한 트랜잭션" vs "0단계를 마치는 순간 POST /api/teams가 먼저 호출되어 teamId 확보" — teamId 존재 시점이
회칙 AI 초안(Q6·R6) 흐름과 직결되므로 어느 쪽인지 확정 요청.

## 3. 요청 (R1~R6)

**R1. `/internal/agent/*` 내부 읽기 API 명세 확정.** "Agent Server가 백엔드에 조회 요청"이라는 서술만
있고 스펙이 없다. LLM 서버 코드가 이미 가정 중인 목록(응답 필드까지 확정 요청):

| API | 용도 | 비고 |
|---|---|---|
| GET `/internal/agent/teams/{id}/budget` | BudgetAuditor 잔액·한도 | 설계서 §7.2 합의분 |
| GET `/internal/agent/teams/{id}/expenses` | 중복 청구 탐지 | 〃 |
| GET `/internal/agent/teams/{id}/profile` | 팀 유형·설정(정책 파라미터) | 경로 미확정 |
| GET `/internal/agent/teams/{id}/members` | PIIMasker 실명→역할 치환 | 〃 (Q: 실명 제공 가능?) |
| GET `/internal/agent/teams/{id}/policy-document` | 회칙 원문+버전 (재인덱싱 fetch) | 〃, R3과 연결 |
| 지출 상세 조회 (C3에서 claim 미포함 확정 시) | 심사 대상 신청 내용 | 신규 |
| 영수증 이미지 조회 경로 (C4) | Intake OCR | 형식 확정 필요 |

**R2. 콜백 필드 매핑표 공동 동결.** LLM 콜백(설계서 §7.2)의 각 필드가 백엔드 어디에 저장·노출되는지
1:1 매핑을 계약서(스키마 diff는 PR)로 동결 요청:

| LLM 콜백 필드 | 풀스택 대응(제안) |
|---|---|
| verdict (approve/reject/escalate) | 상태 전이 + expenses_reviews.final_verdict (ESCALATED 표현은 Q2 결정 따름) |
| category_assigned | review.suggestedCategory (명칭 한쪽으로 통일 요청) |
| opinions[] · reasons{requester,admin} · confidence · mismatch[] | expenses_reviews.detail(json) 저장 제안 — API-045·API-022 detail로 노출 |
| model_version · prompt_version · cost_usd · latency_ms | expenses_reviews.detail(json) — Q9 |
| dry_run | P2 — 필드 자리만 예약 |

**R3. 컨텍스트 갱신(REQ-041)은 '이벤트+버전' 방식 유지 요청.** docx는 "확정값(회칙·예산·승인 조건)을
한 번에 Agent Server로 전달"(원문 push)이라 서술하는데, LLM 서버 계약은
`POST /v1/context/refresh {team_id, change_type(rule|category|params), version}` 이벤트 수신 후
원문은 R1의 policy-document API로 재조회하는 구조다(재인덱싱 중 구버전 유지·원자 전환 때문).
policies에 version/is_current가 이미 있으므로 **이벤트에 version만 실어주면 됨** — 방식 확정 요청.

**R4. v1.1 부가 기능 4종 화면/API 협의 (5주차 통합 예정).** 인수인계 브리핑(REQ-043, `/v1/briefings`),
예산 조정 제안(`/v1/proposals/budget` + 수락 통보 `PATCH /v1/proposals/{id}` + 예산 탭 제안 카드),
회칙 개정 제안(`/v1/proposals/rule-amendment` + "개정안 보기→반영" 흐름), dry-run 사전 문의(P2) —
풀스택 API·화면 대응이 현재 전무하다. 5주차가 통합 목표라 지금 범위·일정을 확정해야 한다.
(수락 실행은 기존 REQ-022/035 CRUD 경유 — 백엔드 신규 트랜잭션은 불필요, ADR-8)

**R5. 알림에 AI 사유 포함(REQ-026·028).** notifications가 user_id·expense_id만 저장하고 조회 시
expenses·users만 조인해 문구를 조립하는 구조라, 에스컬레이션 알림에 AI 보류 사유·불일치 항목을
담을 수 없다. Q2의 소견 저장처가 확정되면 그 테이블을 조립 조인에 추가 요청.

**R6. 리포트·대시보드 AI 요약 + 마법사 회칙 초안 방식 확정.**
- 대시보드 AI 요약(API-024): 동기 GET + "백엔드가 집계 데이터를 넘기고 문구만 받는" 방식이면 LLM이
  **집계 데이터 입력형 동기 엔드포인트**를 신설한다(예: `POST /v1/digests/inline`). 요청에 실을 집계
  필드 목록을 명세 요청. 설계서의 주간 다이제스트(비동기 잡)는 별도 유지 여부 협의.
- 정산 리포트 요약(REQ-019): docx 스스로 "API 추가 필요"로 표기 — 위와 동일 패턴으로 갈지 확정.
- 마법사 회칙 AI 초안(docx ⚠️ 미해결 — 1단계 시점에 teamId 없음): **LLM `/v1/policy-draft`는 원래
  모임 유형 기반이라 teamId가 필요 없다.** 백엔드가 team_type·모임 소개만 넘기는 무-teamId 호출로
  해결 가능 — API-043을 그렇게 조정하는 것을 제안.
