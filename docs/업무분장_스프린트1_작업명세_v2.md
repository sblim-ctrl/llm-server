## 재분배 근거 (2차 개정 — 취업 포트폴리오 가치 균형)

1차 개정 후에도 LLM 코어 3종(로더·하네스·LangSmith)과 신규 에이전트 버티컬 2종(A4·A5)이 모두 개발자 B에 몰려 포트폴리오 가치가 편중된다는 지적이 있었다. 하네스 코어(B1→B2, D1~D3 순차)와 예산 버티컬(A1~A3, D2 오전 하드 데드라인)은 같은 기간의 크리티컬 패스라 한 사람이 병행할 수 없으므로, 2차 개정은 두 트랙을 통째로 교환하고 나머지 과제(A4·A5·B4·B5·B6·A7)로 균형을 맞춘다.

| 포트폴리오 축 | 개발자 A | 개발자 B |
|---|---|---|
| LLM 플랫폼 코어 | 프롬프트 버저닝 로더 · 하네스(PII 마스킹/재시도/토큰·비용 계측) · LangSmith 관측 배선 | — (소비자: C9 태깅 적용·B7a 트레이스 검증으로 사용 경험 확보) |
| 에이전트 버티컬 설계 | DigestWriter 1종 | BudgetPlanner · PolicyDrafter 개정 2종 |
| 멀티모달·벡터 | GPT-4o Vision 영수증 OCR | pgvector 임베딩 군집 탐지(반복 관리자 개입) |
| 신뢰성 엔지니어링 | Vision fail-safe 경로 | 고아 잡 회수·크래시 복구(B5) · 콜백 계약·재시도(B4) |
| 실모드·관측 검증 | review 스모크·마스킹·Digest·Vision (B7b) | 자기 그래프 2종·군집·콜백 실측 (B7a) |

공수: 개발자 A ≈ 5.5일, 개발자 B ≈ 6.25일. 갭은 B1·B2 추정이 상한(1일·1.5일)으로 흐르면 자연 상쇄되며, 지속 시 완화 수단 — ① B4의 콜백 페이로드부는 D4 저녁부터 선착수 가능(B2는 D3 오전 머지됨) ② A6a few_shot은 각 1개로 최소화 가능 ③ D6 합동 리허설의 C4 연결(신규 그래프 3종 중 2종이 B 작성)은 하네스 소유자인 개발자 A가 페어로 지원. 부수 효과로 조율이 단순해진다: B6-client.py(1차 개정의 15분 핸드오프 소멸), B5-레지스트리, B4·B5-pool.py, A2④-backend_client가 모두 셀프 조율화.

## 감사 요점 (왜 이 작업들인가)

**잘 구현됨**: 심사 그래프·병렬 fan-out·opinions reducer(§4.1-4.2), 가드레일 6규칙 순수 함수+테스트 13건(§3.3), checkpointer 재개·fail-safe(§8), SKIP LOCKED 워커(ADR-4), 인덱싱 원자 버전 전환(§4.4-a), 판례 루프(§4.4-b), writers 3종 수치 검증(§4.4-c), MCP 읽기 4종(§5.2), 골든셋 30건+오승인 0% 게이트(§9).

**구조적 최대 리스크 — 시스템이 목 모드(MOCK_LLM=true)에서만 완결**:
- 프롬프트 YAML 로더 부재 → 노드가 `system="(prompts/…yaml에서 로드)"` 플레이스홀더 그대로 LLM 호출 (실모드 시 판정 품질 붕괴)
- PIIMasker가 LLM 프롬프트 경로 미연결 (실명 유출, §4.3·§8 위반) / RetryPolicy·embeddings 타임아웃 없음 / LangSmith 미배선
- model·prompt_version·cost·latency가 콜백·판례에 정적값 → §5.3 재현성·§9 지표 무력화
- Intake Vision OCR 미구현 (정규식 텍스트 파서만)

**계약·신뢰성 버그**: 콜백 category_assigned 누락(§7.2 위반)·재시도 없음, 고아 running 잡(워커 크래시 시 영구 심사중), 비-review 잡 dead 시 지출 에스컬레이션 콜백 오발송, `/mcp` 인증 면제, rule_version=1 하드코딩.

**v1.1 미구현**: proposals 테이블(§6), BudgetPlanner(§4.4-d), PolicyDrafter 개정 모드(§4.4-e), DigestWriter(§4.4-c), 엔드포인트 4종.

### B2. LLM 하네스 — Retry·PIIMasker·호출 메타 (1~1.5일) — **Day 3 오전 머지 데드라인(개발자 B의 B4와 본인 B6·C4 연결의 선행 조건)**
- **파일**: `app/llm/client.py`, `app/schemas/common.py`(`LLMCallMeta`), `app/graphs/review/state.py`(`llm_meta` reducer 키, `team_members` 키), `app/graphs/review/nodes/load_context.py`(멤버 명단 로드), LLM 노드 4곳(메타 스레딩), `models.yaml`(단가 테이블 — C7 pricing), `tests/test_llm_client.py`(신규)
- **구현**:
  - **RetryPolicy**: chat 경로는 `.with_retry()`(langchain-core 1.4.8 지원 확인) 또는 `ChatOpenAI(max_retries=3)`. **embeddings는 Runnable이 아니라 `.with_retry()` 불가** — `OpenAIEmbeddings(max_retries=3, timeout=30)` 생성자 인자로 처리 (§8 사각지대 해소)
  - **PIIMasker**: `chat_structured(…, mask_with: list[dict] | None = None)` — user 프롬프트에 `mask_names` 적용(§4.3 '클라이언트 계층' 이행). 멤버 명단은 `load_context`가 `get_team_members`로 조회해 state `team_members`에 저장 — **실패 시에도 반드시 `team_members=[]` 반환, 노드는 `state.get("team_members") or []`로 접근**(대괄호 접근이면 load_context 없이 노드를 직접 호출하는 기존 단위 테스트가 KeyError — `tests/test_classify_category.py`의 `_state()`가 최소 state만 구성). 판례 검색 쿼리 마스킹(`masked_claim_summary`)과 동일 규칙 유지(표현 공간 일치)
  - **호출 메타**: C4 계약 — 반환형 `tuple[T, LLMCallMeta]`로 변경, 호출부 4곳 일괄 수정(전수 grep 확인: adjudicate·rule_auditor·precedent_auditor·classify_category뿐, writers·eval은 미호출). **usage 추출은 `with_structured_output(schema, include_raw=True)`로 전환 필수**(기본 모드는 AIMessage를 버려 usage_metadata 접근 불가) — `{'raw', 'parsed'}`에서 raw.usage_metadata로 tokens, parsed로 T. 파싱 실패(`parsing_error`) 처리 경로 포함. cost는 models.yaml `pricing:` 단가표(C7 — 본인이 신설)로 계산. 목 모드: tokens=0·cost=0·model=라우팅값. 각 노드가 `{"llm_meta": {agent: meta}}` 반환(merge reducer)
- **완료 기준**: 목 모드 전체 테스트·골든셋 무회귀 + 마스킹 단위 테스트(실명이 user 프롬프트에 안 남는지)

### B5. 워커 신뢰성 (1일) — 원 B 영역(2차 개정으로 복귀) · B1·B2와 독립, 선행은 본인 A3 레지스트리뿐
- **파일**: `app/worker.py`, `app/db/pool.py`, `app/config.py`(`worker_visibility_timeout_sec: int = 300`), `tests/test_worker_recovery.py`(가능 범위)
- **구현**:
  - **고아 잡 회수**: `reclaim_stale_jobs()` — `UPDATE jobs SET status='queued', updated_at=now() WHERE status='running' AND updated_at < now() - interval '%s seconds' RETURNING id`. poll_loop 사이클마다 호출. attempts는 claim 시 증가하므로 재큐만으로 기존 max_attempts→dead 경로에 자연 합류. **알려진 허용 동작**: attempts==max에서 크래시한 잡은 회수 후 1회 추가 실행 뒤 dead — 무한 루프 아님, 코드 주석으로 명시. timeout 300s(p95 15s 대비 충분) — 장시간 잡 오탐 없음
  - **비-review 잡 dead 콜백 수정**: `type=='review'`일 때만 escalate 콜백 전송, 그 외는 finish_job(dead)만 (§8은 지출 심사에 한정된 fail-safe)
  - **체크포인트 부재 방어**: 재시도 경로(attempts>1)에서 `checkpointer.aget(config)`가 None이면 payload로 initial_state 재구성해 START부터 실행. **배선 필요**: checkpointer가 현재 `main()`의 `async with` 지역 변수에 갇혀 있음 — `_review_graph`처럼 모듈 전역(`_checkpointer`)으로 노출해야 run_review_job에서 aget 호출 가능
  - C6: 자신의 A3 레지스트리 위에서 작업(셀프 조율) — 실패 처리·poll_loop 영역만 수정, worker.py 머지는 D5 슬롯. `config.py` 필드 추가는 B3(개발자 A)와 순차 머지
- **완료 기준**: 잡 실행 중 워커 `kill -9` → 재기동 → visibility timeout 후 재큐·완주 확인(수동 시나리오), 재시도 소진 시 review 잡만 escalate 콜백
