■ 먼저 — 저희 API 계약을 전달드립니다 (2026-07-29 추가)

연동 작업 바로 시작하실 수 있도록 저희 쪽 API를 리포에 정리해 올렸습니다. 두 파일입니다.

- docs/openapi.json — 저희가 여는 엔드포인트 14개의 전체 스펙(요청·응답 스키마 포함).
  코드에서 자동 생성한 것이라 이게 곧 현재 계약입니다. Swagger로 보시려면 저희 서버의
  /docs를 열면 됩니다(이 경로는 토큰 없이 열립니다).
- docs/풀스택_연동_계약.md — openapi.json에 안 담기는 3가지를 정리했습니다.
  ① 인증(모든 요청에 Authorization: Bearer 서비스토큰) ② 심사가 비동기라는 것
  ③ 저희가 그쪽으로 보내는 콜백 페이로드 전문과 예시.

특히 ③번을 꼭 봐주세요. 심사 요청(POST /v1/analyze)은 접수만 하고 202로 즉시 응답하고,
결과는 나중에 저희가 그쪽 /agent-callback으로 보냅니다. 그래서 그 수신 엔드포인트는
그쪽에서 만들어 주셔야 하는데, 보내는 쪽 스펙이라 openapi.json에는 안 나옵니다.
실제 직렬화 결과를 예시 JSON으로 넣어뒀으니 그대로 쓰시면 됩니다.

이걸로 "그쪽 → 저희" 호출은 전부 열렸습니다. 반대 방향(저희가 그쪽 내부 조회 API를
호출하는 것)이 아래 1번이고, 그게 실연동의 마지막 관문입니다.

---

안녕하세요, LLM팀입니다. 공유해 주신 API 명세서와 DB 테이블 스키마 잘 받았습니다.
저희 코드와 하나씩 맞춰본 결과, 그동안 막혀 있던 것 5가지가 덕분에 풀렸습니다 — 관리자 검토로
넘어간 건의 AI 소견을 어디 저장할지, escalation_threshold가 금액이라는 것, 카테고리별 예산 한도는
없다는 것, 회칙 버전 관리 방식, 승인/반려를 그쪽에서 실행하신다는 것. 저희 코드에 바로 반영했습니다.
감사합니다.

대신 새로 확인이 필요해진 것이 10가지 생겨서 정리해 드립니다. 급한 순서대로 적었습니다.

■ 1~3번 — 이게 안 되면 실제 연동 자체가 불가능합니다

1. (R1) 저희가 호출해야 하는 내부 조회 API가 명세서에 하나도 없습니다.
심사를 하려면 저희가 백엔드에 8가지를 되물어야 합니다 — 지출 상세, 예산, 팀 설정, 모임 유형,
멤버 명단, 회칙 원문, 영수증 이미지, 관리자 결정 내역입니다. 받은 명세서(API-001~050)는 화면에서
쓰는 API만 담고 있어서 이 8가지가 하나도 없습니다.
→ 내부용 API 명세를 따로 열어 주세요. 경로와 응답 필드만 정해 주시면 저희는 파일 한 곳만 바꾸면
됩니다.

2. AI 심사 API(API-045)가 결과를 그 자리에서 돌려주는 형태로 되어 있습니다.
그런데 지출 건마다 ai_job_id와 ai_dispatched_at 컬럼을 두신 걸 보면 "요청 보내고 나중에 콜백
받는" 구조로 이해했는데, 그렇다면 API-045가 응답하는 순간에는 아직 심사 결과가 없습니다.
→ 접수만 하고 결과는 콜백으로 받는 게 맞을까요? 맞다면 명세서의 응답값 표기만 고치면 됩니다.

3. 저희가 추천하는 카테고리 이름이 그쪽 목록에 하나도 없습니다.
지출 카테고리가 7개(회의·IT_인프라·행사·교육·식비·디자인·기타)로 고정되어 있는데, 저희는 모임
유형별로 다른 카테고리를 씁니다(스터디는 교재/자료비, 친목은 숙박/여행비 같은 식으로 유형당 6개씩).
겹치는 이름이 하나도 없어서, 저희가 추천한 값을 그대로 넣으면 저장이 실패합니다.
→ 카테고리를 늘려 주실 수 있을까요? 지금 7개는 회사 지출 위주라 동아리·친목·동호회에서 쓰는
숙박·대관·교통·장비·홍보가 전부 '기타'로 몰리고, 카테고리별 통계 화면의 의미도 약해집니다.
방법은 두 가지로 생각하고 있습니다 — ① 유형별 대표 카테고리를 합쳐서 목록에 추가 ② 카테고리를
별도 테이블로 빼서 모임 유형별로 다르게 두기. 늘려 주시기 전까지 저희는 지금 목록을 그대로
유지하고 코드를 바꾸지 않겠습니다.

■ 4~7번 — 동작은 하지만 요구사항이 충족되지 않습니다

4. (Q1 재확인) 지출을 등록하는 순간 자동으로 승인되는 것처럼 적혀 있습니다.
API-016 설명에 "팀 설정에 따라 등록 시점의 status가 SUBMITTED / ESCALATED / 승인됨 중 하나로
자동 결정"이라고 되어 있는데, AI 심사를 거치지 않고 승인이 되면 "AI가 함부로 승인하지 않도록 막는
장치"가 무력화되고 AI 심사 자체가 의미가 없어집니다.
→ 등록 시점에는 항상 SUBMITTED이고, 승인은 저희 콜백을 받은 뒤에만 되는 게 맞을까요?
(7/15에도 여쭤봤던 항목입니다)

5. (Q4③) 관리자가 escalationThreshold를 바꿀 방법이 없습니다.
"이 금액 넘으면 무조건 관리자 검토"에 쓰는 값인데, DB에서는 필수값(NOT NULL)인 반면 팀 설정
조회(API-028)·수정(API-029) 어디에도 이 필드가 없습니다. 모임 만들 때(API-009) 응답에만 나옵니다.
→ 조회·수정 API에 이 필드를 추가해 주시고, 모임 생성 시 설정을 생략하면 어떤 기본값이 들어가는지도
알려주세요.

6. (R5) 알림에 AI가 판단한 사유를 담을 수가 없습니다.
알림 문구를 조회 시점에 expenses·users만 조인해서 만드신다고 되어 있는데, AI 소견은 audit_logs에
저장되기 때문에 "왜 관리자 검토로 넘어갔는지"를 알림에 넣을 수가 없습니다.
→ 알림 문구를 만드실 때 audit_logs도 함께 조인해 주실 수 있을까요?

7. 회칙이 바뀐 걸 저희가 알 방법이 없습니다.
회칙을 등록(API-031)하거나 수정(API-033)하셨을 때 저희에게 알려주는 호출이 명세에 없습니다.
저희는 회칙을 미리 읽어두고 심사하기 때문에, 알림을 못 받으면 계속 옛날 회칙으로 심사하게 됩니다.
→ 회칙이 바뀔 때 저희 쪽에 {teamId, 변경유형, 버전} 세 가지만 보내주시면 됩니다. 원문은 저희가
다시 조회하겠습니다. 그리고 API-046(심사 결과 조회)에 "관리자 검토 대기 중에는 결과가 비어서
404를 줄지 null을 줄지 확인 필요"라고 적어두셨는데, 그 경우 소견은 API-022(처리 이력)에서 보이므로
API-046은 null로 고정하시는 편이 프론트에서 단순할 것 같습니다.

■ 8~10번 — 기능 영향은 작고, 서로 안 맞는 부분을 맞추는 것들입니다

8. (R6) 회칙 추천 API(API-044)가 저희 쪽과 형식이 안 맞습니다.
저희가 내려주는 건 조항 목록 + 추천 승인기준(자동승인 한도 등) + 추천 카테고리인데, 명세의 응답은
{제목, 등록방식, 내용} 형태라 추천 승인기준을 담을 자리가 없습니다.
→ 세 가지만 확인 부탁드립니다. ① 모임 만들기 1단계에서는 아직 teamId가 없는데 이 문제를 어떻게
푸시는지 ② 추천 승인기준은 버리는 건지, 아니면 팀 설정 수정(API-029)으로 따로 넣으시는 건지
③ 모임 초기 예산 컬럼을 teams에서 빼셨는데 저희는 초안을 만들 때 그 금액이 필요합니다.
예산 테이블에서 꺼내주시면 될까요?

9. 대시보드 AI 요약(API-024)을 어떤 방식으로 만들지 정해야 합니다.
저희는 이 기능을 다음 스프린트로 미뤄뒀는데 명세에 정식으로 들어가 있어서 다시 잡았습니다.
→ 그쪽에서 집계한 숫자를 넘겨주시고 문구만 받으시는 방식이면, 저희가 그에 맞는 API를 새로
만들겠습니다. 넘겨주실 집계 항목 목록만 알려주세요. 정산 리포트 요약도 같은 방식으로 갈지 함께
정하면 좋겠습니다.

10. 명세서에서 두 군데가 어긋나 있습니다.
① audit_logs의 event_type 목록에 값이 비어 있는 자리가 하나 있고, 설명에는 EDITED가 언급되는데
목록에는 없습니다. 그리고 "AI 심사가 끝나서 소견을 저장했다"에 해당하는 이벤트가 없어서, 저희
콜백이 도착했을 때 어떤 값으로 기록되는지 알 수 없습니다. ② 모임 초기 예산이 DB(teams)에서는
빠졌는데 API-009 요청·응답에는 그대로 남아 있습니다(8번 ③과 같은 건입니다).
→ event_type 목록을 확정해 주세요.

11. 저희 API의 필드 표기가 두 군데 섞여 있습니다. 어느 쪽으로 맞출지 정해 주세요.
① 심사 요청(POST /v1/analyze)은 받을 때는 jobId·expenseId처럼 camelCase인데, 돌려드리는
응답은 job_id·external_job_id처럼 snake_case입니다. 잡 조회(GET /v1/jobs/{id}) 응답도
같습니다. ② 콜백은 최상위가 전부 camelCase인데 opinions 배열 안의 similar_cases 하나만
snake_case로 나갑니다.
→ 저희 판단으로는 전부 camelCase 통일이 자연스러운데, 그쪽 파서에 이미 반영하신 게 있으면
그 기준을 알려주세요. 저희는 파일 한두 곳만 고치면 됩니다. 임의로 바꾸면 계약이 또 어긋나서
현상 그대로 전달드립니다.

■ 지난번(7/15) 질문 중 아직 답을 못 받은 것들

이번 문서로도 풀리지 않아 그대로 남아 있습니다. 참고만 해주세요.

- (Q3) 관리자 결정을 저희가 주기적으로 가져오는 건 — 응답 필드는 저희가 제안드렸고, 어느 테이블에서
  오는 값인지·몇 초 주기인지·인증은 어떻게 할지 세 가지만 남았습니다. 위 1번과 함께 답해주시면 됩니다.
- (Q6) 영수증 미리보기용 임시 토큰 스펙 — 예전에 API-050으로 부르던 건인데 이번에 그 번호가 정산
  리포트 조회로 바뀌어서, 번호 없이 기능으로 다시 여쭙니다.
- (C3) 심사 요청에 실어 주실 필드 3가지 — 결과를 어디로 콜백할지 같이 보내주실지, 시험 실행(dry_run)
  자리를 남겨둘지, '심사 목표'를 자유 텍스트로 주실지 정해진 값 중 하나로 주실지.
- (C2) 승인/반려는 저희가 추천만 드리고 그쪽에서 실행하시는 방향으로 확정된 것으로 이해했습니다.
  남은 건 둘 — 콜백에 대한 응답으로 최종 반영 결과를 돌려주실 수 있는지, 콜백이 중복 도착했을 때
  중복 처리를 막는 책임이 어느 쪽인지입니다.
- (R2) 저희 콜백 항목과 그쪽 DB 필드 간 매핑표 — 위 10번 ①(event_type)과 같이 정하면 한 번에 끝납니다.

급한 순서는 1·2·3번(연동 자체가 막힘) → 4·5·6·7번 → 8·9·10·11번 순입니다.
전부 데모 일정에는 영향 없는 항목이니 편하신 시점에 답 주시면 됩니다. 감사합니다!
