안녕하세요, LLM팀입니다. 지난번 드린 질의요청서(7/15) 중 아직 답이 필요한 항목만 추려서
다시 정리해 드립니다. 우선순위 순서대로 7가지입니다.

1. (Q3) 관리자가 AI 판정을 뒤집었을 때(override), 그 결정을 저희가 어떻게 받아올 수 있을까요?
저희가 주기적으로 확인하러 가는 방식(pull)으로 방향은 합의됐고, 응답 필드는 다음과 같이
제안드립니다: id 오름차순으로 {id, expense_id, decision, is_override, override_reason,
decided_by, decided_at}. 이 구성이 맞는지, 어느 테이블에서 오는 값인지, 몇 초 주기로
확인하면 되는지, 인증은 어떻게 하는지만 확정해 주시면 됩니다.

2. (Q6) 영수증 미리보기 기능에 쓸 임시 접근 토큰 스펙을 알려주세요. JWT인지, 유효기간·
1회용 처리 방식이 어떻게 되는지 확정되면 저희 쪽 검증 로직을 만들 수 있습니다.

3. (C3) 심사 요청을 보내주실 때 필드 3가지만 더 확인 부탁드립니다: 결과를 어디로
콜백할지(callback_url) 함께 보내주실지, 시험 실행 여부(dry_run) 자리를 남겨둘지,
'심사 목표' 필드를 자유 텍스트로 주실지 정해진 값 중 하나로 주실지.

4. (C2) 승인/반려를 저희가 직접 실행하지 않고 "이렇게 하면 좋겠다"는 추천만 콜백으로
드리는 방식으로 하기로 했는데요, 그 콜백에 대한 응답으로 최종 반영 결과를 저희에게
돌려주실 수 있는지, 콜백이 중복 도착했을 때 중복 처리를 막는 책임은 어느 쪽이 지는 게
맞을지 확인 부탁드립니다.

5. (R2) 저희가 보내는 콜백 항목과 그쪽 DB 필드 간 매핑표를 확정해 주세요. 예를 들어
category_assigned 값이 그쪽의 suggestedCategory에 대응되는지 같은, 이름 통일이 필요합니다.

6. (C3) 지출 신청 상세 내용(제목·금액 등)을 저희에게 요청에 안 실어 주시는 방향으로
저희 쪽은 이미 개발을 마쳤습니다. 이 방향이 맞는지 최종 확인 부탁드리고, 맞다면
저희가 그 상세를 조회할 수 있는 내부 API를 열어주셔야 합니다.

7. (R6) 정책(회칙) 추천 API를 팀ID 없이(모임 유형과 소개만으로) 호출하는 방식으로
바꾸자고 저희가 제안드렸는데, 검토 가능하실까요?

급한 순서는 1·2번(다른 기능 전체가 막혀 있어요) → 3·4·5번(심사 코어 마무리) →
6·7번 순입니다. 전부 데모 일정에는 영향 없는 항목이라 편하신 시점에 답 주시면 됩니다.
감사합니다!
