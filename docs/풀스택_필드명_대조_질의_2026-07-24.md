## 0. 배경 — 두 문서는 **서로 다른 구간**을 규정한다 (모순 아님)

```
[프론트] ←──①──→ [백엔드] ←──②──→ [Agent Server(LLM)]
```

| 문서 | 규정 구간 | 모임 식별자 |
|---|---|---|
| `full stack api 명세서.pdf` | **① 프론트 ↔ 백엔드** 공개 API 50종 | `teamId` |
| `bravo 기술아키텍처설계서` 표16·18·19 | **② 백엔드 → Agent Server** 내부 심사 요청 | `organizationId` |

새 명세서의 **API-045(ai-review)는 요청값이 `-`(본문 없음)** 이고 *"서버 내부에서 호출되는
내부용 API"* 로만 기술돼 있다 — **백엔드가 Agent Server로 무엇을 보내는지는 이 명세서의
범위 밖**이며, `bravo 설계서`가 그 구간을 규정한다.

그리고 bravo 설계서 표18이 다음과 같이 명시한다:

> **organizationId** — 지출이 속한 모임의 ID**(teams.id)**. Agent Server가 이 값으로
> team_settings(자동승인 한도·에스컬레이션 임계값)와 policies(회칙)를 백엔드에 조회 요청.

→ **`organizationId`와 `teamId`는 같은 값(teams.id)의 다른 별칭.** 따라서 llm-server의
현행 수신 필드명(`organizationId`)은 bravo 설계서와 정합하며, 두 문서 간 충돌은 아니다.
**아래 FQ1은 "확인"일 뿐 변경 요청이 아니다.**

> 참고: 명세서 번호가 이전 버전과 밀려 있다. 현행 기준
> **API-044=AI 정책 추천 / API-045=AI 지출 심사(ai-review) / API-046=AI 심사 결과 조회(review-result)**.
> llm-server 코드 주석 일부가 구 번호(API-043/044/045)를 참조하고 있어 계약 확정 시 함께 정정한다.

## 2. 질의 항목

### 🔴 FQ2. 콜백 판정 필드명과 값 형식

- **현행**: 콜백에 `verdict` 키로 `approve` / `reject` / `escalate` (**소문자**) 전송.
- **명세서**: API-045/046 응답 필드는 `finalVerdict`. 상태값은 `SUBMITTED` / `ESCALATED` /
  `APPROVED` / `REJECTED`(**대문자**)로 표기돼 있으나, **`finalVerdict`의 값 형식은 명시 없음.**
- **질문**:
  1. 콜백 키를 `finalVerdict`로 변경하면 되는가? (백엔드가 `verdict`로 매핑 중이면 현행 유지)
  2. 값은 대문자(`APPROVED`)인가 소문자(`approve`)인가?
  3. AI의 `escalate` 추천은 백엔드 status `ESCALATED`와 1:1 대응인가?

### 🔴 FQ3. 자동승인 판단 주체 — **두 문서가 다르게 읽힌다**

- **bravo 설계서**: *"Agent Server가 영수증 항목화(OCR) 후, **team_settings.auto_approve가
  켜져 있을 때만** auto_approve_limit · escalation_threshold 기준으로 자동승인 여부를 판단"*
  → **Agent Server(우리)가 판단.**
- **API 명세서 API-016**: *"팀 설정(API-029)의 autoApprove, autoApproveLimit 값에 따라
  **등록 시점의 status가 자동으로** SUBMITTED / ESCALATED / APPROVED 중 하나로 결정됨"*
  → **백엔드가 등록 시점에 결정.**
- **현행 llm-server**: `guardrail_gate.py:24`가 **0번 규칙**으로 `auto_approve`가 꺼져 있으면
  금액·판단과 무관하게 무조건 escalate.
- **질문**:
  1. 등록 시점 status 자동 결정과 AI 심사는 어떤 순서로 실행되는가?
  2. 최종 권한은 어느 쪽인가? (LLM팀 전제: **AI는 추천만, 확정은 백엔드**)
  3. 백엔드가 이미 APPROVED로 결정한 건도 우리에게 심사 요청이 오는가?

### 🔴 FQ7. 콜백 주소(`callback_url`)를 요청에 담아 보내는가

- **bravo 설계서**: *"백엔드가 LLM 팀에 분석을 요청하면서 **'분석 끝나면 이 주소로 결과를
  보내줘'라는 콜백 주소를 함께 전달**합니다"*
- **현행 llm-server**: `AnalyzeRequest`(`app/schemas/analyze.py`)에 `callbackUrl` 필드가
  **없다.** 콜백 주소는 서버 설정값으로 고정 사용 중(`app/tools/backend_client.py`).
- **질문**: 요청 payload에 콜백 주소가 실제로 포함되는가? 포함된다면 키 이름은?
  (조건부 트랙 ① `callback_url` 항목과 직결)

### 🔴 FQ8. 콜백 제한 시간 — 확정치와 동시 요청 규모

- **bravo 설계서**: *"일정 시간(예: **30초**) 안에 콜백이 오지 않으면 배치/스케줄러가 해당 건을
  자동으로 **ESCALATED**로 전환합니다"*
- **영향**: 제한 시간을 넘기면 **우리 심사 결과가 도착해도 무시**되고 사람 검토로 넘어간다.

#### LLM팀 실측 결과 (2026-07-28, 실모드 9건 · 골든셋 표본)

| 구간 | 소요 |
|---|---|
| 큐 대기 (워커 폴링 주기 2초) | 최대 2.0초 |
| 심사 그래프 실행 | 중앙값 **3.3초** / 평균 3.1초 / **최대 4.4초** |
| 콜백 HTTP 왕복 | 수백 ms |
| **단건 end-to-end (추정)** | **약 5~7초** |

노드별 평균: `adjudicate` 1.25초 · `precedent_auditor` 1.22초 · `rule_auditor` 0.81초 ·
`budget_auditor` 0.04초(코드 계산이라 LLM 미호출) · 나머지 순수 함수 0초.
영수증 금액 불일치 건은 LLM 호출 없이 조기 에스컬레이션되어 **0.4초**에 종료.

**→ 단건 기준 30초 예산은 충분히 충족한다(최악 케이스 여유 약 +25초).**

#### 다만 동시 요청이 몰리면 초과한다

현재 워커는 **1개 인스턴스가 1건씩 순차 처리**한다(`app/db/pool.py` — `FOR UPDATE SKIP
LOCKED LIMIT 1`). 큐에 동시에 쌓이면 대기가 누적된다:

| 큐 순번 | 대기 | 심사 | 총 소요 | 30초 |
|---|---|---|---|---|
| 5번째 | 16초 | 4초 | 20초 | ✅ |
| 7번째 | 24초 | 4초 | 28초 | ⚠️ 임계 |
| **8번째** | 28초 | 4초 | **32초** | ❌ 초과 |

**→ 단일 워커 기준 동시 7~8건이 한계.** 워커 인스턴스를 늘리면 비례해 해소되며
(SKIP LOCKED 구조라 중복 처리 없음), **적정 대수는 예상 동시 요청량에 따라 정한다.**
